# course-handout-builder

## 這份講義是給誰、拿來做什麼

學習者是伺服器海外業務，正在用 12 週準備外商 **Pre-sales／Solutions Engineer** 的面試（主軸；TMM／Evangelist／PMM／TAM 為備選，見 `00_study_plan/01_syllabus.md` 第 0 節）。他**每天只有 1 小時**，所以講義是**自學 35 分鐘**用的材料，不是文章、不是摘要：它要讓人先自己想、再讀、再講出來、最後被測。讀完一份講義，學習者要能（1）用自己的話講機制，（2）說出每個數字的口徑與來源，（3）把它翻成售前桌上的四種對話：對客戶 CxO／採購、對客戶工程師、這會怎麼改變配置與報價、怎麼回應客戶的反對意見。隔天早上的測驗會直接從講義結尾的 K 點清單抽題，所以 K 點寫得準，整套學習系統才轉得動。

寫作依據是《Make It Stick》與《學生為什麼不喜歡上學？》；具體規則在 `references/learning-science-rules.md`，請在動筆前讀一次，寫完對照一次。

## 工作流程

### 1. 解析輸入，定位到課綱

接受三種輸入：`W01D02` 代碼、「第 1 週第 2 天」、或主題名（如「HBM」）。對應關係：

- 週主題、核心問題、必讀文章（★）：`00_study_plan/01_syllabus.md` 第 5 節。
- 每週五天的切分與每日來源文章：`references/weekly-day-plan.md`。主題名輸入時，用這份表找最接近的週／日。
- 第 1 週的 K 點已經寫好在 `00_study_plan/quizzes/week01/k_points.md`，第 1 週講義的 K 點清單必須與它一致（可增不可改）。

若輸入的日已有講義（`00_study_plan/handouts/wNN/dMM_*.md` 存在），先問是要重寫還是修訂；不要默默覆蓋。

### 2. 取材：只轉述，不創作

這是整個 skill 最重要的規則。講義裡每一個數字、每一條機制，都要能指回 repo 的某一行。原因很直接：學習者會把這些東西講給面試官與客戶聽，一個編出來的數字會讓整份作品集失去可信度；而且測驗解答要附 `file:line`，來源不存在就出不了題。

做法：

1. 用 `grep -n '^#' <文章>` 看大綱，用 `sed -n 'a,bp'` 讀需要的段落。不要整篇吞進 context，一份講義通常只需要來源文章的 2～4 個小節。
2. 邊讀邊記三張清單：**概念**（最多 7 個，每個一句話）、**數字**（值、單位、口徑、`file:line`）、**誤區**（文章明說或你從文章推得的常見誤解）。
3. 文章沒寫、你也不確定的事，寫「待查」並說明去哪查（官方 datasheet、哪份文件）。不要用訓練記憶補數字。
4. 上游文章是簡體中文。引用原文可保留簡體並用引號，自己寫的部分一律繁體；術語保留英文（HBM、warp、PagedAttention）。
5. 來源行號以 repo 現況為準；寫完讓 `scripts/check_handout.py` 驗證每個 `file:line` 是否存在且不超過檔案長度。

### 3. 依骨架寫講義

骨架在 `references/handout-template.md`，章節編號與標題**固定**（檢查腳本靠它們定位）。每節有字數預算，總計約 1100～1500 個中文字，對應 35 分鐘含測驗。超過就砍概念（最多 5 個），不要砍第 3 節、第 5 節、測驗與 K 點；這三塊是 Pre-sales 最常用到的。

幾個寫作決定，以及為什麼：

- **第 0 節「先想再讀」3 題不給答案**。先嘗試再學的記憶保持率明顯高於直接讀；答案在第 7 節課後測驗裡自然會對到。
- **第 1 節用一個客戶情境開場，裡面要有衝突**（客戶的說法與事實相反、兩個方案打架、預算與需求對不上）。人記得住的是故事與衝突，不是定義。情境要具體到有卡型號、有數字。
- **第 2 節每個概念先給具體例子再給定義**，而且至少兩個不同代際或廠商的例子（A100 與 H100、HBM 與 GDDR），單一例子無法抽象。
- **第 3 節數字表的「口徑」欄是必填**：單向／雙向、dense／sparsity、卡規格／系統可用、廠商規格／實測、日期。客戶和面試官最常追問的就是這一欄。
- **第 5 節 Pre-sales 口徑**四段：客戶 CxO／採購 30 秒、客戶工程師 3 分鐘、配置建議、反對意見應對，寫法見 `references/role-angles.md`。「配置建議」一段最重要：要寫出今天的機制會改變報價單上的哪一項（卡型、張數、機型、網卡、記憶體），以及還要再問客戶什麼。寫的時候真的切換聲音，不要只是改稱呼。
- **第 6 節精緻化提問**問「為什麼」與「和之前學的什麼連起來」，不問「是什麼」。
- **第 7 節課後提取 5 題**：第 1 題自由回憶，至少 1 題計算或口徑題，不出選擇題；題型代號與規則見 `00_study_plan/02_assessment_spec.md` 第 3 節。答案放文末摺疊區，不放題目旁邊。
- **第 8 節 K 點 6～8 條**，格式嚴格：`WwwDdd-Kn | 難度 | 可檢驗的陳述 | file:line | 受眾`。每條只含一個可驗證的事實或機制，陳述裡要帶數字與口徑。這是隔天測驗的題源，寫得像考題的答案。

### 4. 視覺

GitHub 會渲染 Mermaid，所以圖用 Mermaid；每份講義 1～3 張，放在第 2 或第 3 節。圖要說明**機制**（資料怎麼走、層級誰包誰、代際怎麼變），不要只是裝飾。型錄與安全語法在 `references/visual-patterns.md`；repo 既有的圖片可以用相對路徑嵌入（`../../../01_hardware_architecture/.../img/x.png`），嵌入時註明出處。

### 5. 輸出與索引

- 路徑：`00_study_plan/handouts/wNN/dMM_<英文 slug>.md`，slug 小寫、底線分隔、2～4 個詞（`d02_gpu_memory_hbm.md`）。
- 若 `00_study_plan/quizzes/weekNN/k_points.md` 不存在，建立它，把本講義的 K 點按日追加（格式同第 1 週）。存在則追加本日區段，不改已有條目。
- 在 `00_study_plan/handouts/README.md` 的索引表加一列：週、日、講義連結、主題、產生日期。

### 6. 驗證

```bash
python3 .claude/skills/course-handout-builder/scripts/check_handout.py 00_study_plan/handouts/w01/d02_gpu_memory_hbm.md
```

修到沒有 `ERROR`。`WARN` 看一下是否合理（例如簡體字數偏高通常是引用太多原文，改成自己的話）。最後跑一次 repo 的 fence 檢查習慣：腳本已含圍欄閉合檢查。

## 便宜模型最常犯的錯（請逐條自查）

| 錯                                               | 為什麼糟                                   | 改法                                                     |
| ------------------------------------------------ | ------------------------------------------ | -------------------------------------------------------- |
| 把來源文章整段搬進第 2 節                        | 超過 35 分鐘預算，且重讀不等於學會           | 每個概念 ≤ 120 字，用自己的話，留 `file:line` 讓人回去讀 |
| 數字沒有 `file:line` 或口徑欄空白                | 測驗出不了題、面試被追問就垮                 | 查不到就寫「待查」                                       |
| 情境開場寫成定義（「HBM 是一種…」）              | 沒有衝突就沒有記憶掛鉤                       | 先寫客戶說了什麼錯話或兩難                               |
| 課後測驗出選擇題                                 | 辨認不等於提取                               | 改自由回憶／簡答／計算／判斷並說理                       |
| Pre-sales 口徑只是改稱呼（「各位工程師」「各位長官」）| 沒練到切換                               | CxO 版不得出現 warp、SM 等詞；工程師版必須有機制與數字    |
| 配置建議只寫「建議用高階卡」                     | 不能直接用在報價                             | 寫出具體配置項與條件，附「要再問客戶」的問題              |
| 用簡體寫自己的句子                               | 違反本層語言規定                             | 自己的話一律繁體，引用可簡體加引號                       |
| Mermaid 節點文字含括號、引號、斜線導致渲染失敗   | GitHub 上整張圖消失                          | 節點文字用 `["..."]` 包，避免 `()` `/` `#`              |
| K 點寫成大標題（「HBM 很重要」）                 | 無法出題                                     | 寫成帶數字與口徑的可檢驗陳述                             |

## 最小範例

輸入：「產生 W01D02 的講義」

動作摘要：讀 `01_syllabus.md` 第 5 節 W1 列 → 讀 `references/weekly-day-plan.md` 的 W1 D2 → 讀 `quizzes/week01/k_points.md` 的 D2 區段 → `grep -n '^#'` 與 `sed -n` 讀 `02_gpu_memory.md:9-75`、`01_hbm_evolution.md:21-70` → 依模板寫 `handouts/w01/d02_gpu_memory_hbm.md`（情境：客戶拿 RTX 5090 的 1.79 TB/s 說「跟 A100 差不多，為什麼貴十倍」）→ 跑 `check_handout.py` → 更新 `handouts/README.md`。

輸出的 K 點區段節錄：

```text
W01D02-K5 | 3 | 總頻寬 = 堆疊數 × 每堆疊頻寬；A100：5 × 1024 bits × 1.593 GHz × 2（DDR）÷ 8 = 2039 GB/s | 01_hardware_architecture/performance/01_hbm_evolution.md:50-56 | 工程師
```
