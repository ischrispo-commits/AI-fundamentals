# Google TPU 101

對於習慣了 CUDA 的工程師來說，對 GPU 的認知往往建立在 SM、Warp 排程、寄存器和 Shared Memory 之上。開發者透過 Kernel、Grid/Block 配置和 shared memory tile 化，挖掘硬件算力，關注的核心是「每個執行緒在幹什麼」、「訪存是否 coalesced」以及「Warp 的分支發散情況」。

TPU 要解決的問題和 GPU 類似：高吞吐地跑深度學習推理和訓練。但 Google 並沒有「再造一個 GPU」，而是從頭圍繞深度學習工作負載做了一個幾乎完全不同的架構 [1,2]。這套架構，從硬體到軟體，都圍繞兩個核心原則展開：深度學習的主力工作就是大規模矩陣乘加（MatMul/GEMM）加上少量逐元素運算，以及模型規模持續變大，多晶片協同是常態而不是例外。

圍繞這兩個原則，TPU 在硬體和軟體層面做了兩組非常鮮明的取捨。在硬體層面，TPU 放棄了複雜的 SIMT + Warp 排程機制、傳統通用 Cache 層級和精細可程式設計的 shared memory，以及面向圖形和通用計算的指令級靈活性。取而代之的是固定規模的 systolic array 矩陣乘單元（MXU）、高頻寬弱 Cache 語義的 HBM 加本地 scratchpad，以及晶片間高頻寬面向 collective 的專用互聯。

在軟體層面，TPU 同樣放棄了以 Kernel 為中心、由工程師手工指定 launch 配置的程式設計模型，以及顯式管理 shared memory、warp 和指令序列的「手工排程權」。相應地，軟體能力集中到了以 **XLA** 為核心的圖級編譯器 [3] 上：由它承擔 HLO / StableHLO 層的跨框架可移植性 [3,5]，以及針對特定硬體（TPU Pod）的全域性圖最佳化和集體通訊排程。

所以，本文的兩條主線是：

- 從硬體和軟體兩個維度，回答 TPU 在架構上「放棄了什麼」，又「強化了什麼」；
- 從工程實踐的角度，回答會寫 CUDA MatMul 的工程師在 TPU 上如何「寫出」一個 MatMul。

閱讀時可以帶著一個簡單的對照問題：在 GPU 上，你最佳化的是「執行緒如何跑得更快」；在 TPU 上，你則要學會最佳化「矩陣如何更順暢地流過整個系統」。

## 1. TPU 的設計出發點：為什麼 Google 沒有「再造一個 GPU」

### 1.1 從 GPU 的「通用性負擔」說起

GPU 的成功很大程度上來自「通用性」：既能跑圖形，又能跑科學計算、影片編解碼和深度學習。為了支撐這種通用性，GPU 架構天然揹負了不少歷史包袱。

首先是圖形流水線遺產，早期 GPU 為圖形渲染而生，Shader 模型、紋理單元、固定功能管線等設計長期影響著硬體形態。其次是 SIMT + Warp 排程複雜度，單指令多執行緒（SIMT）模型需要硬體負責 Warp 形成、切換和分支掩碼管理，這帶來了複雜的控制邏輯。最后是 Cache、Shared Memory 和 Register 的多層次管理成本，為了兼顧不同訪問模式，GPU 掌握著多級 Cache、軟體管理的 shared memory 和大規模暫存器檔案，程式設計師需要在這些層級之間不斷做權衡。

但對現代深度學習工作負載而言，需求抽象其實要簡單得多 [2]。主力是大規模 dense 或 semi-dense 的矩陣乘加（MatMul、Conv），資料流大多是可預測的，很少出現完全隨機、無規律的訪問模式，控制流複雜度相對較低，長而規整的算子鏈條非常常見。換句話說，GPU 為了通用性保留了大量「可能會用到」的能力，但深度學習主力工作負載並不總是需要這些能力，甚至在某些場景下，這些通用機制本身會成為最佳化的負擔。

### 1.2 TPU 的根本假設

基於在 Google 內部大規模深度學習工作負載的經驗，TPU 團隊做了一個激進但清晰的假設 [1,2]：

- **訓練 / 推理 ≈ 大規模矩陣乘加 + 少量逐元素運算。**

在這個假設下，TPU 在設計上與 GPU 產生了根本分歧。GPU 主要最佳化「如何讓執行緒跑得更快」，重點在於單個執行緒或 Warp 的效率、指令排程和訪存 coalescing。而 TPU 則最佳化「如何讓矩陣一直在流動」，重點在於 systolic array 的填滿率、資料進入和流出陣列的效率，以及在整個 Pod 級別讓矩陣不斷流動。

這直接驅動了後續硬體和軟體的取捨：

- 在硬件上，TPU 可以犧牲靈活性，換取為矩陣乘專門打造的 systolic array 和資料流路徑。
- 在軟體上，TPU 可以把「排程權」交給編譯器，工程師只需描述計算圖本身，Kernel 級別的執行細節不必過問。

## 2. 硬體架構對比：SM + Tensor Core vs MXU + Systolic Array

### 2.1 GPU 架構快速回顧（作為對照系）

先快速回顧一下 GPU 結構，作為後文的對照系。

在一個典型的 NVIDIA GPU 上：

- SM 的核心職責包括：

  - 負責 Warp 形成和排程；
  - 負責指令的發射與流水線控制；
  - 協調 Tensor Core 與標量 / 向量單元共同工作。

- Tensor Core 的工作方式可以概括為：
  - Tile-based MMA：以固定大小的矩陣 tile 為基本操作單元；
  - 透過 WMMA、CUTLASS 或編譯器自動生成的指令來觸發；
  - Kernel 作者需要做大量 tile 劃分和 shared memory 管理，才能把 Tensor Core 利用率拉起來。

從這個視角看，GPU 是一個典型的 **執行緒中心（thread-centric）** 架構：一切最佳化幾乎都可以還原為「某個執行緒 / Warp 在什麼時間訪問了什麼地址、發出了什麼指令」。

---

### 2.2 TPU 核心計算單元：MXU（Matrix Multiply Unit）

在 TPU 上，核心計算單元不再被稱為 Tensor Core，而是 Matrix Multiply Unit（MXU）。MXU 並不是簡單放大版的 Tensor Core，而是圍繞 systolic array 專門設計的矩陣乘機器 [1,2]。

MXU 的關鍵特徵包括：

- 固定規模的 **systolic array**（官方架構頁口徑：v6e 與 TPU7x 為 256 × 256，此前世代為 128 × 128 ALU 陣列）[1,2]：
  - 每個陣列元素負責簡單的乘加（MAC）操作；
  - 資料沿著陣列的行、列「心跳式」推進。
- 硬體級資料推進（dataflow in hardware）：
  - 陣列內的資料流由硬體自動推動，無需每個執行緒顯式 load/store；
  - 一旦資料被送入陣列，之後的傳播和累加幾乎不需要指令介入。
- 幾乎沒有指令級排程概念：
  - MXU 更像一個「一次性啟動的大型流水線」，很少表現為頻繁發射的指令流；
  - 對程式設計模型來說，MXU 是不可見的，你看不到「某條矩陣乘指令」。
- 一個 TPU TensorCore 由 MXU + 向量單元 + 標量單元組成 [1]：
  - MXU 負責大塊矩陣乘；
  - 向量單元負責逐元素運算、簡單非線性；
  - 標量單元負責控制流、地址生成和資料搬運。

這組設計的直接結果是：TPU 在硬件上 **放棄了執行緒級別的精細控制權**，換取了一個為大規模矩陣乘專門鋪好的流水線。

從對比視角來看，GPU Tensor Core 和 TPU MXU 在多個維度上存在顯著差異。在排程單位方面，GPU 采用 Warp 或 Instruction 級別的排程，而 TPU 則採用資料流排程方式。程式設計可見性方面，GPU 的 Tensor Core 對程式設計師是可感知的，而 TPU 的 MXU 對程式設計模型來說是完全不可見的。在 Tile 控制方面，GPU 需要程式設計師或 XLA 進行控制，而 TPU 則由純硬體控制。最終目標方面，GPU 主要關注提升單次 MMA 性能，而 TPU 則致力於最大化持續吞吐。

---

### 2.3 Systolic Array：TPU 的「核心硬體結構」

為什麼 TPU 會選擇 systolic array，而不是繼續沿用 GPU 的 SIMT + Tensor Core 模型？

從硬體的「第一性原理」來看，矩陣乘的核心在於重複的 MAC 操作和可預測的資料訪問模式。systolic array 正好滿足這兩個特點：

- 每個陣列單元只做非常簡單的乘加；
- 資料可以沿著規則的方向以固定節奏推進；
- 同一個資料在陣列中被多次複用，而不需要反覆訪問外部儲存。

如果用資料流來對比 GPU 和 TPU：

- 在 GPU 上，一般的模式是：

  - Load → Compute → Store（迴圈往復）；
  - 每一個 tile 的輸入、輸出都需要顯式 load/store；
  - 訪存模式、shared memory 複用都需要工程師手工設計。

- 在 TPU 上，systolic array 的典型模式更接近：

  - **Load once → Flow through → Accumulate**；
  - 資料在陣列中不斷向前流動，沿途經過多個 MAC 單元並被累加；
  - 一旦進入陣列，資料在陣列內部的傳播幾乎不再消耗外部頻寬。

這組取捨的代價和收益都很直接：任意訪問模式的通用負載能力被捨棄，規則資料流換來高吞吐和高能效。

### 2.4 記憶體與資料通路設計

TPU 的記憶體層次和 GPU 看起來類似：都有 HBM，也有本地更快的儲存。但設計哲學完全不同 [1]。

TPU 的記憶體哲學可以概括為採用高頻寬 HBM 作為權重和激活的大容量儲存，每個 TensorCore 擁有本地向量記憶體（VMEM / scratchpad）並由編譯器顯式管理 [1]，採用極弱的 Cache 語義儘量避免「硬體猜測」，以及在編譯期確定資料佈局與資料移動路徑，儘可能在編譯階段決定「哪些資料何時放在哪」。

對比之下，GPU 的做法是把片上 SRAM 分為 shared memory 和各種 Cache，Cache miss 是常態需要依賴硬體猜測訪問模式，工程師需要在 shared memory、暫存器和全域記憶體之間做精細排程。

在這裡，代價是失去「硬體自動猜測訪問模式」的便利，換來的是「由編譯器全域性規劃資料流」的可預測性。

### 2.5 SparseCore：從 v4 起的稀疏加速單元

從 TPU v4 開始，Google 在 TPU 晶片中加入了一類新的硬體單元：SparseCore [1]。它不是 MXU 的替代，而是專門為大規模推薦和 embedding 模型設計的稀疏加速器。

SparseCore 的定位是面向大規模推薦和 embedding 模型的稀疏操作加速 [1]，與 MXU 形成互補關係：MXU 負責 dense 和 semi-dense 計算，而 SparseCore 負責高度稀疏訪問。

在架構設計上，SparseCore 采用 tile-based dataflow 處理器架構，每個 tile 擁有本地 SPMEM 與處理單元 [1]。資料佈局與快取策略由 XLA 或上層軟體顯式控制，而非依賴硬體自動快取。透過分析 embedding 訪問模式，系統能夠決定哪些向量快取於本地 SPMEM，哪些駐留在 HBM 中 [1]。

可以看到，哪怕是在面向稀疏訪問模式的硬體設計上，TPU 也依然堅持「由軟體（編譯器）顯式決定資料位置」的設計思想。

## 3. TPU 芯片 ≠ TPU 系統：從單卡到 TPU Pod

### 3.1 TPU 的 scale-first 設計

「多晶片協同是常態」並非 TPU 與生俱來的前提：TPU v1 是一張 PCIe 單卡推理加速器；從 v2/v3 起，Pod 形態才逐步成形（v3 組成 Pod，v4 引入 3D torus 拓撲與 OCS 光交換），「模型持續變大、多晶片協同訓練是常態」自此成為設計假設。因此，TPU 的設計採用了 **scale-first** 的理念。在單晶片層面，TPU 追求在給定功耗和麵積約束下最大化矩陣吞吐；而在多晶片層面，則透過專用互聯（ICI）和 Pod 拓撲，把多個 TPU 打造成一個「系統級加速器」。

與之對應，GPU 世界以單卡為先，單卡效能和靈活性放在首位；H100 平台本身已帶 NVLink 4 + NVSwitch 硬體互聯，面向更大規模的系統級互聯（NVSwitch 交換域、NVL 超節點）屬於後發補強，在這類形態普及之前，跨節點擴展更多依賴軟體棧（NCCL、Horovod 等）協同。在互聯技術方面，TPU 使用的是 ICI（Inter-Chip Interconnect），GPU 叢集中常見的是 NVLink 或 InfiniBand。兩者都提供高頻寬低延遲通訊，差別在於 TPU 的 ICI 自 v3/v4 按 Pod 拓撲設計起就與 collective 通訊緊密繫結 [1,2]。

### 3.2 TPU Pod 的系統級抽象

在系統層面，一個 TPU Pod 是按照 2D/3D torus 拓撲組織起來的 [1]。每個 TPU 主機板包含多個晶片，主機板之間透過 ICI 連線，全 Pod 的 ICI 形成一個規則的二維或三維環形拓撲。在這種設計下，collective 操作（例如 AllReduce、AllGather）在硬體層就是一等公民。

與 GPU 叢集相比，差異在系統級互聯的成熟時點：GPU 側單節點能力強，NVSwitch、NVL 超節點這類系統級互聯是後發逐步補上的；TPU 則從 v3/v4 起就按 Pod 拓撲設計，系統級是一等公民，Pod 自身就是一個面向大規模訓練的整體系統。

這背後的取捨是：GPU 把資源優先投給單卡通用算力和彈性軟體生態，TPU 把資源優先投給系統級矩陣吞吐和深度學習專用互聯。

### 3.3 Cloud TPU 部署模型與拓撲細節

在 Cloud TPU 上，Google 提供的是以 TPU VM 為基礎的程式設計模型 [2]。TPU VM 直接將 TPU 繫結到一個虛擬機器實例上，提供「類本地裝置」體驗 [2]，而 Pod 配置在物理上提供多芯片、跨機櫃的 2D 或 3D torus 拓撲。

ICI 的特性包括面向 AllReduce 和 collective 通訊最佳化的專用互聯 [1]，其延遲、頻寬與拓撲設計都假設「多晶片同步訓練」是最主要場景。

對工程實踐而言，這種設計意味著程式設計模型天然偏向資料並行和張量切分，「多行程多 GPU 自己拼」的空間很小 [2,4]。效能最佳化更偏向於如何把計算圖高效地分佈到整個 Pod 上，而不是單純追求單卡把 FLOPS 吃滿。

這也是 TPU 在系統層面的取捨：相容雜亂多樣拓撲的靈活性被捨棄，換來特定拓撲下大規模同步訓練的效率。

## 4. 軟體棧總覽：從 CUDA 到 XLA 的正規化躍遷

### 4.1 CUDA 軟體棧回顧

在 CUDA 世界里，軟體棧大致可以拆成三層。CUDA Runtime 和 Driver 負責裝置管理、記憶體分配、Kernel 啟動、上下文切換等基礎功能。Kernel 程式設計模型讓工程師使用 C++ 或 CUDA C 編寫 Kernel，顯式指定 Grid 和 Block 配置。手工效能調優路徑包括修改 block size、grid 維度、執行緒佈局，手工 tile 化資料並搬到 shared memory，以及使用 WMMA 或 CUTLASS 映射到 Tensor Core。

在這個模型下，開發者擁有極大的控制權，幾乎能決定每個執行緒在每個時鐘週期做什麼，但這也意味著必須為效能負全責。

### 4.2 TPU 軟體棧的核心：XLA

在 TPU 世界里，XLA 是整個軟體棧的核心 [3]。它是一個面向深度學習的編譯器，可以做 ahead-of-time 或 just-in-time 編譯。XLA 的定位是從 TensorFlow、JAX、PyTorch/XLA 等前端接收計算圖 [2,3,4]，以 HLO 或 StableHLO 作為中間表示進行圖級最佳化 [3,5]，並針對 TPU、GPU、CPU 等不同後端生成高度最佳化的執行程式碼。

XLA 的最佳化與執行路徑包括將前端計算圖 lower 為 HLO 或 StableHLO 表示，在圖級別進行算子融合（Fusion）、記憶體佈局最佳化和並行劃分，把矩陣計算切分成適配 MXU 的 tile（v4/v5 世代為 128 × 128）[2]，以及針對特定後端生成目的碼並快取編譯結果以複用 [3,4]。

在 TPU 上，不存在很多開發者已經習慣的概念，例如「TPU Kernel」、「TPU shared memory」或「TPU launch configuration」。這些都被 XLA 收編了，開發者在 TPU 上編寫的是「計算圖」而不是「Kernel」。

### 4.3 主流前端棧：TensorFlow / JAX / PyTorch XLA

今天在 Cloud TPU 上常見的前端主要有三類。TensorFlow + XLA 透過 `tf.function(jit_compile=True)` 或編譯標誌啟用 XLA [2]，官方文件建議使用靜態 shape、規則 batch 和規整張量佈局以匹配 MXU 偏好 [2]。

JAX 本質上以 XLA 為預設編譯後端 [3]，透過 `jit`、`pmap`、`pjit` 等原語控制編譯和分散式並行。

PyTorch / XLA 透過 Lazy Tensor 機制收集 IR 圖，再下发到 XLA 編譯 [4]，儘可能保留 PyTorch 的使用體驗，同時讓模型跑在 Cloud TPU 或 XLA GPU 上 [4]。

### 4.4 HLO / StableHLO 與可移植性

在 XLA 內部，計算圖會被表示為 HLO（High Level Operations）[3]。HLO 描述算子、shape、佈局以及它們之間的資料依賴，是圖級最佳化的工作物件，不是單條指令。

StableHLO 則是在 HLO 之上的一個穩定規範 [5]，面向多框架和多編譯器的可移植 HLO 規格，目標是在 TensorFlow、JAX、PyTorch 等前端與 XLA、IREE 等後端之間建立穩定介面。

對 CUDA 工程師而言，這意味著需要從「寫 Kernel + Launch Config」升級到「理解編譯後圖長什麼樣」，效能調優更多發生在「圖級別變換 / 結構化建模」的層面，單 Kernel 拆解的思路在這裡用處不大。

換句話說，TPU 在軟體層面交出了對每個執行緒行為的精細控制權，換來了對整個計算圖的全域性掌控力。

## 5. 矩陣乘法對照解析：CUDA vs TPU

> 本節是全文的「認知錨點」，目標是讓開發者 **真正理解 TPU 的程式設計方式差異**。

本節將以典型的矩陣乘法（MatMul）為例，對比「在 CUDA 裡控制了什麼」與「在 TPU 上交出了什麼」。

---

### 5.1 CUDA 中的 MatMul：開發者在控制什麼？

假設要在 CUDA 上實現一個簡單的矩陣乘 `C = A x B`，即使不使用 WMMA，也通常會採用類似下面的 Kernel 結構：

```cpp
// 一個典型的 CUDA 矩陣乘 Kernel，展示開發者手工控制的要素
__global__ void matmul_kernel(const float* A, const float* B, float* C,
                              int M, int N, int K) {
  // 計算當前執行緒負責的輸出位置
  int row = blockIdx.y * blockDim.y + threadIdx.y;
  int col = blockIdx.x * blockDim.x + threadIdx.x;

  // 使用 shared memory 做 tile 化載入
  __shared__ float Asub[BLOCK_SIZE][BLOCK_SIZE];
  __shared__ float Bsub[BLOCK_SIZE][BLOCK_SIZE];

  float acc = 0.0f;
  for (int t = 0; t < (K + BLOCK_SIZE - 1) / BLOCK_SIZE; ++t) {
    // 每個執行緒負責載入部分 tile 資料
    int tiledRow = row;
    int tiledCol = t * BLOCK_SIZE + threadIdx.x;
    if (tiledRow < M && tiledCol < K) {
      Asub[threadIdx.y][threadIdx.x] = A[tiledRow * K + tiledCol];
    } else {
      Asub[threadIdx.y][threadIdx.x] = 0.0f;
    }

    tiledRow = t * BLOCK_SIZE + threadIdx.y;
    tiledCol = col;
    if (tiledRow < K && tiledCol < N) {
      Bsub[threadIdx.y][threadIdx.x] = B[tiledRow * N + tiledCol];
    } else {
      Bsub[threadIdx.y][threadIdx.x] = 0.0f;
    }

    __syncthreads();

    // 在共享記憶體 tile 上做局部乘加
    for (int k = 0; k < BLOCK_SIZE; ++k) {
      acc += Asub[threadIdx.y][k] * Bsub[k][threadIdx.x];
    }

    __syncthreads();
  }

  // 把結果寫回全域記憶體
  if (row < M && col < N) {
    C[row * N + col] = acc;
  }
}
```

在這個 Kernel 里，開發者顯式控制了：

- Grid / Block 劃分：`blockDim`、`gridDim`，決定每個 block 處理多大 tile；
- Tile 大小選擇：`BLOCK_SIZE`；
- Shared memory 使用：哪些資料放 shared memory，如何複用；
- 每個執行緒負責哪些 load/store，以及怎樣避免越界；
- 指令層面是否使用 WMMA / Tensor Core。

本質上，開發者在 **顯式描述執行策略**：如何在給定硬體上完成這次矩陣乘。

---

### 5.2 TPU 中的 MatMul：開發者「放棄」了什麼？

在 TPU 上，同樣的矩陣乘可以寫成非常簡單的形式，例如在 JAX 中：

```python
# 在 JAX + XLA + TPU 上執行矩陣乘，展示開發者只描述數學運算
import jax
import jax.numpy as jnp

def matmul(a, b):
  # 只描述數學運算本身
  return a @ b

# 使用 jit 觸發 XLA 編譯
jit_matmul = jax.jit(matmul)

# 在 TPU 裝置上建立輸入張量並執行
a = jnp.ones((M, K), dtype=jnp.float32)
b = jnp.ones((K, N), dtype=jnp.float32)
c = jit_matmul(a, b)  # 實際在 TPU MXU 上執行
```

從這個呼叫方式看，開發者似乎「什麼都沒做」：沒有 Kernel，沒有 blockDim / gridDim，沒有 shared memory 的顯式宣告，更沒有任何 warp 相關的參數。

但在背后，XLA 做了很多在 CUDA 世界里需要手工完成的事情 [2,3,4]：

- Shape 推斷：根據 `a` 和 `b` 的 shape 推斷矩陣乘的具體維度；
- Tile 拆分：把矩陣乘拆解為適合 MXU 的 tile（v4/v5 世代為 128 × 128）[2]；
- Systolic array 映射：決定每個 tile 如何映射到 systolic array 中；
- 資料流排程：決定資料如何從 HBM / VMEM 流入 MXU，又如何被累加和寫回。

本質上，開發者在 TPU 上 **放棄了 Kernel 級的執行權**，只描述「數學本身」，把執行策略全部交給編譯器。

這背後還有一個重要細節：與硬體偏好的對齊 [2]。

- MXU 以固定規模的 tile 為基本單位進行計算（v4/v5 世代為 128 × 128，v6e 與 TPU7x 為 256 × 256）[1,2]；
- XLA 會在必要時自動 padding 到硬件友好的尺寸（例如 8、128 的倍數）[2]；
- 高性能 Cloud TPU 程序通常要求 batch size 或特徵維度滿足這些對齊約束，避免大量無效 padding [2]。

這意味著，**開發者仍然在為效能做決策**，但決策的物件從「執行緒 / block / shared memory」變成了「shape / batch size / 資料佈局」。

---

### 5.3 思維模型對比總結

| **問題**     | **CUDA**    | **TPU**    |
| ------------ | ----------- | ---------- |
| 誰決定 tile  | 程式設計師      | XLA        |
| 誰排程計算   | Kernel      | 編譯器     |
| 最佳化粒度     | 指令 / Warp | 計算圖     |
| 效能調優方式 | 手工        | 結構化建模 |

### 5.4 一個 Conv + BN + ReLU 的對照 case（將在正文展開）

再來看一個更復雜但更貼近日常訓練的算子組合：Conv + BN + ReLU。

在 CUDA 視角下，三個算子往往對應多個 Kernel，期間存在多次 HBM 讀寫。開發者會嘗試做 Kernel fusion，把 BN 和 ReLU 融到 Conv kernel 里，需要顯式考慮共享記憶體複用、訪存 coalescing 和暫存器壓力。

在 TPU / XLA 視角下，XLA 傾向將 Conv + BN + ReLU 融合為一個或少量 HLO / Fusion 區域 [3,4]。編譯器負責在 MXU 和向量單元之間安排資料流路徑、臨時結果存放位置，工程師更多從「圖結構是否易於融合」的角度改寫模型，而不是手寫融合後的 kernel。

這裡再次體現 TPU 的軟體取捨：每個算子如何落到硬體上不再由工程師直接安排，統一排程和融合由編譯器完成。

## 6. TPU 的優勢、限制與適用邊界

### 6.1 TPU 的「甜點區」

綜合硬體和軟體的取捨，TPU 的「甜點區」非常清晰 [1,2]：

- 大模型訓練：尤其是 Transformer 類模型，在大規模 Pod 上的資料並行或張量並行；
- 高吞吐推理：對單樣本延遲不敏感、對吞吐敏感的服務場景（例如批次離線推理）；
- 高度規則的 dense / semi-dense 計算：矩陣乘、卷積、規整的 MLP 等。

在這些場景中，TPU 的 systolic array、高頻寬 ICI 和 XLA 圖級最佳化可以最大化發揮效果。

### 6.2 TPU 的天然短板

與之對應，TPU 也有自己的天然短板 [2,4]：

- 非規則計算：高度稀疏、動態結構的圖計算，可能難以高效對映到 MXU；
- 細粒度控制流：大量 `if` 分支、動態迴圈等，可能導致圖形態複雜、編譯困難；
- 小 batch / 低算力密度場景：難以填滿 MXU 和整個 Pod 的算力，吞吐優勢發揮不出來。

### 6.3 在 Cloud TPU 上寫程式的實用 Checklist

如果開發者已經習慣在 CUDA 上做調優，可以把以下建議當作遷移到 Cloud TPU 時的對照參考 [2,3,4]。

在**模型與資料選擇**方面，應優先選擇 dense 或 semi-dense 計算密集型模型（如 Transformer、CNN 等）[2]，避免高度動態 shape，儘量在編譯期就固定張量形狀 [2,4]，如果必須使用動態 shape，也應儘量限制在少數幾個模式。

在**張量尺寸與佈局**方面，需確保關鍵維度（batch 或 feature）是 8 或 128 的倍數 [2]，注意 NHWC 或 NCHW 等佈局對 MXU tile 利用率的影響，並在可能的情況下，從模型設計階段就考慮這些對齊約束。

在**編譯與調優**方面，利用 XLA profiling、TPU Profiler、XProf 等工具分析 tile 利用率和 padding 情況 [2,3]。優先透過「重構計算圖」和「增加並行度」來提升吞吐，而不是摳單次 step 的 latency。對於熱點子圖，可以考慮在 HLO 或 StableHLO 層面做結構化改寫，「TPU Kernel」並不存在，無從手寫。

## 7. 總結：從 CUDA 工程師到 TPU 使用者，需要轉變什麼

回到本文一開始提出的兩個核心問題：

- TPU 在硬體和軟體層面「放棄了什麼」，又「強化了什麼」？
- 如果你會寫 CUDA MatMul，那麼 TPU 的 MatMul 是如何「被寫出來」的？

從硬體層面看，TPU 放棄了執行緒級和 warp 級的精細排程權，通用複雜的 Cache 層級和顯式可程式設計的 shared memory，以及面向廣義 GPGPU 的通用負載適配能力。

TPU 強化了以 MXU 和 systolic array 為核心的矩陣乘流水線 [1,2]，由編譯器顯式管理的資料流和本地 scratchpad，以及 ICI 和 Pod 拓撲下的系統級矩陣吞吐能力 [1,2]。

從軟體層面看，TPU 放棄了以 Kernel 為中心、以 launch 配置為關鍵調參手段的程式設計模型，以及在每個算子上由工程師決定「跑在哪些執行緒上、如何分 tile」的自由度。

TPU 強化了以 XLA 為核心的圖級編譯和跨算子融合能力 [3]，以 HLO 和 StableHLO 為中間層的跨框架可移植性 [3,5]，以及針對特定硬體（TPU Pod）的全域性圖排程和並行劃分。

而對 CUDA 工程師來說，從 GPU 世界走向 TPU 世界，要經歷三處轉變：

- 從「寫 kernel」到「寫計算圖」：GPU 上開發者為每個 Kernel 調參；TPU 上寫的是計算圖，排程交給編譯器統籌。
- 從「控制硬件」到「相信編譯器」：GPU 上幾乎能追蹤每個執行緒的行為；TPU 上要假設編譯器會用滿 MXU 和 Pod 拓撲，再用 HLO 和 Profiling 驗證。
- 從「單卡最佳化」到「系統級吞吐」：GPU 上最佳化多落在單卡、單 Kernel 如何跑滿；TPU 上更該關心整個 Pod 上的矩陣流動是否順暢，包括 batch size、分散式並行策略和資料佈局。

接受這些轉變之後，在 TPU 上寫 MatMul 就不再涉及手寫 Kernel，工作重心轉為把模型和資料組織成便於編譯器在 systolic array 和 Pod 上高效執行的形狀。

最後說明一點：本文的架構論述以 v2-v5 世代為基線；自 v6e（Trillium）與 TPU7x 起，部分規格已有變化（如 MXU 擴為 256 × 256），涉及具體數字時以官方架構頁為準（截至 2026-11）。
