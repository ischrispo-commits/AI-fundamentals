## 一、背景：互連的舊秩序與 CXL 的登場

處理器與外部裝置之間的通訊，長期以來由兩條互不交叉的路線承擔：**PCIe 序列匯流排**連線 CPU 與裝置（GPU、NIC、FPGA、儲存），**DDR 並行匯流排**連線 CPU 與記憶體。二者各有所長，但都帶著與生俱來的結構性缺陷——而正是這些缺陷，在 AI/ML 工作負載興起後變成了不可迴避的瓶頸。

PCIe 的成功建立在兩點上：向後相容與開放生態。它承擔"控制面"職責時無可挑剔——裝置發現、配置、DMA、中斷，全部透過非一致的 load-store 語義完成。但**非一致意味著裝置無法快取系統記憶體**：每次訪問都穿越 Root Complex，無法利用時間/空間區域性性，無法執行原子操作序列。當加速器（GPU、智能 NIC、PIM 裝置）需要與 CPU 共享同一份資料結構時，只能整塊搬運、軟體同步——這正是 AI 推理中常見的"資料先拷入裝置、算完再拷回"模式背後的協議根源。

DDR 的問題則是**引腳效率**。論文給出了一個決定性的對比：x16 Gen5 PCIe 端口（32 GT/s）用 64 根訊號引腳提供 64 GB/s/方向（雙向 128 GB/s）；DDR5-6400 用約 200 根引腳只提供 50 GB/s——**PCIe 每引腳頻寬高出 DDR 約 8 倍**（128/64 = 2 GB/s/引腳 vs 50/200 = 0.25 GB/s/引腳）。（論文原文此處寫作"256 GB/s"，疑為筆誤：32 GT/s × 16 lanes 的物理上限即 64 GB/s/方向，且論文自己的 8× 結論按 128 GB/s 雙向計算才成立。）PCIe 引腳原則上完全可以替代 DDR 承擔記憶體互連，但它不提供一致性與記憶體語義，裝置側記憶體無法對映進可快取的系統地址空間，因此替代無從談起。記憶體牆的根源不只是延遲，還有這條協議層面的"各管一段"。

第三條路線是歷史上反覆嘗試過的**對稱一致性互聯**：Intel QPI/UPI、AMD Infinity Fabric、IBM Bluelink、NVIDIA NVLink，以及試圖把一致性推向更大範圍的 CCIX 與 OpenCAPI。對稱互聯要求每個節點實現相同的快取一致性演算法並跟蹤全部狀態，複雜度高、各架構實現差異大、演進緩慢；而且並非所有場景都需要一致性——記憶體擴容（Challenge 2）與資源池化（Challenge 3）需要的是**記憶體語義**而非完整一致性。對稱路線因此始終沒有成為跨廠商的統一標準。

CXL 的誕生是上述三條線索的匯合。Intel 早在 2005 年就有"在 PCIe 上加簡化一致性機制"的想法，並先後在 PCIe 3.0 中加入原子語義、嘗試過共享記憶體控制器（SMC）方案——但 PCIe 3.0 僅 8.0 GT/s 的頻寬讓池化失去意義。2019 年，PCIe 5.0 的 32.0 GT/s 與成熟的線纜生態讓頻寬不再成為障礙，Intel 以自有協議 Intel Accelerator Link（IAL）為基礎，**於 2019 年 3 月將 IAL 1.0 更名釋出為 CXL 1.0**，與 Alibaba、Cisco、Dell、Google、Huawei、Meta（2019 年時名 Facebook）、Microsoft 等共同成立 CXL 聯盟。此後競爭標準（CCIX、GenZ、OpenCAPI）相繼合併入局，聯盟成員膨脹至約 250 家公司，版本演進為：CXL 1.0（2019.3）→ CXL 1.1（2019.9，加入合規測試機制）→ CXL 2.0（2020.11）→ CXL 3.0（2022.8），全程向后兼容。

CXL 的設計哲學可概括為三個詞，它們貫穿三代協議：**非對稱**（主機承擔一致性編排，裝置只需實現簡化 MESI，降低裝置端實現門檻）、**向后兼容**（複用 PCIe 物理層、槽位、軟體棧，裝置可以從 PCIe 平滑遷移）、**開放**（多協議分層，裝置只需實現與自己用途相關的協議子集）。這套哲學是理解後續所有技術選擇的鑰匙。

## 二、問題：四個驅動 CXL 的行業挑戰

論文將 CXL 要解決的行業問題收斂為四個挑戰，全部有具體量化支撐，而非泛泛之談。

**挑戰一：系統記憶體與裝置記憶體之間缺少一致性訪問。** PCIe 裝置不能快取系統記憶體，加速器訪問共享資料必須整塊搬運並在軟體層用屏障機制防止 CPU 與裝置併發衝突。這直接阻礙了 AI/ML、智能 NIC、近記憶體計算（PIM）等"CPU 與裝置同時訪問同一資料結構"的新范式。PIM 尤其受困：沒有一個標準化的方式讓 PIM 裝置一致性訪問可能駐留在 CPU 快取層次中的資料，程式設計模型因此極度笨重，阻礙了 PIM 的普及。

**挑戰二：記憶體可擴展性跟不上算力增長。** 計算呈指數增長，DDR 卻因引腳效率低而拖了後腿：加 DDR 通道帶來平台成本上升與訊號完整性難題；DRAM 每比特成本近年持平，而 DDR 命令集（Refresh、Bank Pre-charge 等）又與 DRAM 介質強繫結，阻礙 ReRAM、3D XPoint 等新介質類型被採納。PCIe 引指令碼是更優的記憶體互連載體（每引腳 8 倍頻寬、支持 retimer 長距離佈線、單 DIMM 功耗可超 15W），唯獨缺一致性與記憶體語義。

**挑戰三：資源滯留（stranding）導致的算力與記憶體雙重浪費。** 一台伺服器的計算、記憶體、I/O 裝置被物理繫結為"一台機器"，當工作負載峰值需求波動時，每台伺服器都必須按峰值超額配置記憶體與加速器：算力跑滿的伺服器記憶體閒置，記憶體吃緊的伺服器卻無法從機架上其他伺服器借用。阿里、AWS、Google、Meta、Microsoft 的資料均報告了低資源利用率，stranding 同時帶來功耗、成本與可持續性三重損失。根本原因是**資源的耦合粒度過細**——資源屬於伺服器，而不屬於資源池。

**挑戰四：分散式系統的細粒度資料共享。** Web 級應用（搜索、社交內容合成、廣告選擇）的 partition/aggregate 模式中，查詢更新通常小於 2kB；分散式資料庫依賴 kB 級頁面，共識協議更新更小。這些更新對延遲極度敏感——4kB 資料在 50 GB/s 鏈路上傳輸不足 2μs，但資料中心網路通訊延遲普遍超過 10μs，**傳輸時間只佔等待時間的五分之一**。一致共享記憶體可以把通訊延遲壓縮到亞微秒級。

四者輕重不同：挑戰一與二指向單機內的協議能力（一致性與記憶體語義），挑戰三與四指向系統級重構（池化與跨主機共享）。三代 CXL 的演進順序恰好對應了這個由內而外的次序——先解決單機內的語義，再解決機器間的組合方式。

## 三、方案：三代協議的演進之路

### 3.1 CXL 1.1：單機內的一致性與記憶體語義

CXL 1.1 是整座大廈的地基：它在 PCIe 物理層之上覆用了三套協議，定義了三種裝置類型，並確立了低延遲的實現路徑。後續兩代的所有能力都建立在這套分層之上，因此值得逐層拆解。

**三協議複用同一物理層。** CXL.io、CXL.cache、CXL.mem 被動態複用在同一對 PCIe 鏈路上（論文圖 2 的多協議複用模型）。CXL.io 基於 PCIe，承擔裝置發現、狀態上報、虛擬地址翻譯與 DMA，是**所有裝置必選**的協議；CXL.cache 讓裝置可以快取系統記憶體；CXL.mem 讓裝置記憶體對映為可快取的主機記憶體（Host-managed Device Memory，HDM），主機獲得"本機記憶體 + 裝置記憶體"的統一檢視。三者的存在與否，恰好劃分出三種裝置類型：**Type 1**（僅 io+cache，如智能 NIC）、**Type 2**（io+cache+mem，如帶本地記憶體的 GP-GPU/FPGA）、**Type 3**（僅 io+mem，如記憶體擴展裝置）。裝置按用途實現協議子集——這是 CXL 控制裝置複雜度的核心手段。

**68 位元組 Flit 與低延遲路徑。** 三種協議的傳輸單元是 Flit（流控單元）：2 位元組協議 ID + 64 位元組負載 + 2 位元組 CRC。64 位元組負載與 cache line 等長，使 CXL.cache/mem 無需分組/重組開銷；協議 ID 帶冗餘編碼（Hamming 距離 4 且重複兩次），CRC 可檢測 64 位元組負載內最多 4 個隨機位翻轉。與 PCIe 的 TLP/DLLP 變長分組相比，Flit 化讓鏈路層與事務層路徑大幅縮短，再加上**在物理層做多路複用**（而非更高層）、128b/130b 編碼可協商旁路等最佳化，CXL.cache/mem 的延遲被壓到與"本地 socket 的 DDR 訪問"同一量級——這正是"與對稱互聯相當、但只承擔非對稱複雜度"的關鍵兌現。

**CXL.cache：主機編排的簡化一致性。** 裝置透過 CXL.cache 快取主機記憶體，一致性協議採用經典 MESI，但**主機負責全部對等快取跟蹤**，裝置從不直接與對等快取互動——這是非對稱設計的精髓。協議由每方向三條通道構成（Request/Response/Data），裝置側 D2H Request 提供 4 類 15 個命令（Read、Read0、Read0-Write、Write），主機側 H2D Request 用於對裝置快取發起 Snoop。地址翻譯透過 PCIe ATS 擴展完成：裝置實現 DTLB 快取頁表項，CXL 擴展 ATS 以區分"允許走 CXL.cache"與"僅限 CXL.io"的訪問。協議細節中最見功力的是衝突處理：GO（Global Observation）訊息必須排在同地址後續 Snoop 之前（Req-to-Snoop 情形），保證裝置先感知自己已獲 E 狀態所有權、才能正確響應後續 Snoop；Evict-to-Snoop 情形下，髒資料驅逐在途時到達的 Snoop 必須拿到 M 態資料，隨後到達的 GO_WritePull 雖仍需返回資料但必須標記為"可能過期"，主機據此丟棄。這些規則保證了多代理併發下的正確性，而代價全部由主機承擔。

**CXL.mem：主機可快取訪問的裝置記憶體。** 協議只有兩對通道（M2S 的 Request/RwD 與 S2M 的 NDR/DRS），通道間不強制排序以換取簡單與低延遲。CXL 3.0 術語將 HDM 分為兩類：**HDM-H**（host-only coherent，主機獨佔一致性，典型於 Type 3 記憶體擴展器，可選 2-bit Meta Value 供主機使用）、**HDM-D**（device-managed coherent，典型於 Type 2 加速器，裝置透過 DCOH agent 跟蹤主機快取狀態，並透過 **Bias Flip 流程**——基於裝置側 Bias Table 記錄 Host-S/Host-A/Device 三態——主動翻轉地址的"偏好"以回收所有權）。HDM-D 的一致性仲裁最終落在裝置側：裝置是它擁有地址的一致性的最終裁決者。

**協議依賴圖：無環保證的死鎖自由。** 論文用協議依賴圖（L1=CXL.cache、L2=host-specific、L3=CXL.mem 三層的通道依賴關係）論證協議內部與跨協議層的**無死鎖性**：只要依賴圖無環，就不會出現通道間迴圈等待。這是一致性協議設計中罕見的"可證偽"論證方式，也為 CXL 3.0 的 Back-Invalidate 通道加入時如何維持無環提供了檢驗工具。

### 3.2 CXL 2.0：資源池化與執行時重構

CXL 1.1 把記憶體語義帶給了單台機器，但資源仍然繫結在機器上——stranding 依舊。CXL 2.0 的目標是把資源從"屬於某台伺服器"變成"屬於一個可重分配的池"：**與其為兩台伺服器按峰值分別配置記憶體，不如按均值配置一個共享池**，執行時把空閒資源動態重分配給吃緊的主機。這個轉變依賴一組新能力：熱插拔、單級交換、記憶體與裝置池化、記憶體 QoS 與全域性持久重新整理（GPF），並由 Fabric Manager 統管池分配。

**交換與虛擬層次。** CXL 2.0 引入單級交換：主機看到的 CXL 拓撲被抽象為虛擬層次（VH）——每台主機擁有獨立的 Virtual CXL Switch（VCS），只含分配給它的橋與裝置。Flit 依據虛擬橋路由，每個主機-裝置對之間只有一條路徑（有向樹拓撲）。裝置池化建立在此之上：標準裝置是 Single-Logical-Device（SLD，同一時刻只歸屬一台主機）；**Multi-Logical-Device（MLD）**則把一個 CXL.mem 裝置的資源切成最多 16 個邏輯裝置（LD），按 256MB 粒度經 Set-LD 命令建立，各 LD 可同時歸屬不同主機。LD-ID 只存在於交換與裝置之間的鏈路上，對主機不可見——交換根據主機埠打標籤。CXL 2.0 的拓撲由此被嚴格限制為"單交換、單路徑"，這個限制要到 CXL 3.0 才被打破。

**"池"的主機檢視：多個獨立裝置，而非一個聚合裝置。** 這裡澄清一個常見誤解：交換機並不把眾多記憶體裝置"聚合"成一個大裝置呈現給主機——每台主機列舉到的是分配給它的每個裝置（SLD）或每個 LD（MLD），各自擁有獨立的 PCIe 配置空間、CDAT 屬性表與 HDM decoder，裝置粒度在主機側完全可見。"一個統一記憶體池"的統一性來自軟體層：主機側 HDM decoder 可跨多個裝置做地址交錯（Linux 下 `cxl create-region -m -w 2 -g <粒度> mem0 mem1`——`-m` 指示位置參數為 memdev 名，`-w` 與 memdev 數量一致，把一段 HPA 條帶化到多個 memdev）；OS 記憶體層級（memory tier）把它們歸入同一慢記憶體層統一排程；應用層再以 mmap + 偏移約定實現劃分與共享。另一層語義邊界同樣值得記住：標準 CXL 2.0 下同一 SLD 或同一 LD 同一時刻只歸屬一台主機——多主機併發訪問同一裝置地址的硬體一致性共享記憶體是 CXL 3.0 借 Back-Invalidate/GFD 才進入規範的；2.0 時代的跨主機共享只能以"裝置/LD 歸屬切換 + 軟體協議"實現。

**Fabric Manager 與池管理。** 裝置如何動態繫結到主機，由 CXL Fabric Manager（FM）裁決：FM 可以是主機上的軟體、BMC 固件、交換內嵌韌體或專用裝置，透過 Component Command Interface（CCI）經帶內（MMIO）或帶外（MCTP：SMBus/I2C、PCIe、USB、串口）下发命令。繫結（bind）需四個參數：交換 ID、虛擬橋 ID、物理端口 ID、邏輯裝置 ID；解綁（unbind）支援三種語義——等待主機停用、熱移除並等待主機、**強制熱移除**（後者允許 FM 與不配合的主機協作，例如裸金屬雲中歸屬第三方客戶的主機）。裝置歸屬變更對主機表現為標準熱插拔事件，無需重啟。QoS 層面，CXL.mem 響應訊息攜帶 DevLoad 欄位報告裝置負載，主機據此調節注入速率；多源場景用源節流（source throttling）控制各源對 MLD 資源的佔用上限。

**主機軟體的新角色。** 池化把"靜態資源配置"變成了"執行時事件"。傳統記憶體拓撲經 ACPI 靜態表（SRAT/HMAT）在開機時固化；CXL 2.0 引入 **CDAT（Coherent Device Attribute Table）**——記憶體裝置執行時熱插時，主機讀取其 CDAT 寄存器，獲得內部 NUMA 域、記憶體區間、頻寬與延遲屬性，由 OS 分配空閒 HPA 並程式設計 HDM decoder。裝置驅動的還是 PCIe 驅動框架，但記憶體資源的管理從韌體靜態配置轉向 OS 執行時管理。

### 3.3 CXL 3.0：Fabric 與規模躍遷

CXL 3.0 的目標是把 CXL 2.0 的池化從"單交換、16 台主機"推向"多級交換、4096 個端點（主機、記憶體、加速器、NIC 均可）"。論文給出的核心矛盾是：CXL 2.0 的單路徑樹拓撲源於 PCIe 的 ordering 規則——只要一致性/有序性依賴樹形路由，規模就被鎖死。CXL 3.0 的每一步都是對這把鎖的拆除。

**64 GT/s 與 256 位元組 Flit。** 頻寬翻倍依賴 PCIe 6.0 的 PAM-4 電訊號（4 電平，每 UI 編碼 2 bit），但 PAM-4 的眼圖高度/寬度顯著劣化，首位元錯誤率高達 10⁻⁶，必須引入前向糾錯（FEC）。CXL 3.0 定義了兩種 256B Flit：常規型（8B Reed-Solomon CRC + 3 路交錯單符號糾錯 FEC）與**延遲最佳化型（128B LO Flit）**——由兩個 128B 子 Flit 組成，FEC 跨整個 256B 共享，但每個 128B 半 Flit 有獨立 6B CRC。關鍵工程洞察是 **CRC 先於 FEC 執行**：CRC 約 10 級邏輯閘，FEC 約 50 級，先查 CRC 在無錯路徑上省約 2ns（x16 鏈路），且 128B 的累積延遲還略優於 32 GT/s 下的 68B Flit。出錯時再累積全 Flit 做 FEC、重查 CRC。Flit 模式（68B/256B/LO）在鏈路協商時確定，與執行速率解耦——即使 64 GT/s 鏈路降速到 32 GT/s，LO Flit 模式仍然生效。

**UIO：無序 I/O 拆掉樹的鎖。** PCIe ordering 規則是樹拓撲的制度性根源。CXL 3.0（隨後被 PCIe 6.0 採納）定義 **Unordered I/O（UIO）**：在 VC1–VC7 上傳輸完全無序的事務，**排序責任上移到源節點**——每個 UIO Write 都帶 completion（實質上是非 posted 的），生產者必須先等資料寫完成、再寫 Flag；UIO Read 正常返回帶資料的 completion。跨流控類與流控類內部的排序要求全部取消，於是任意源-目的對之間可以走多條路徑、仍保住生產者-消費者語義。VC0 保留傳統有序傳輸用於向後相容。一句話概括：**樹拓撲是為了全域性有序，UIO 把有序性從"全網屬性"降級為"源點行為"，全網就可以是任意拓撲。**

**Back-Invalidate：繞過主機的一致性回寫。** CXL.mem 新增 S2M 方向的 Back-Invalidate 通道（BISnp/BIRsp），裝置可主動把主機快取中的副本作廢（對應新的 HDM-DB 記憶體類型，Type 2/3 均支持）。由此解鎖三個用法：其一，**裝置直連裝置**——裝置經 UIO 直接訪問交換上其他裝置的 HDM 記憶體，命中 I/S 態直接服務，需要一致性時才用 BI 反向回寫主機（論文例：NIC→記憶體直連 8 跳，經主機 16 跳往返）；其二，**Type 2 裝置可用 snoop filter 取代全量目錄**——容量未命中時用 BI 驅逐，從而能把大塊本地記憶體對映進 HDM-DB 區域；其三，**多主機硬體一致性共享記憶體**——記憶體裝置（MLD 或 GFD）維護目錄（每 cache line 兩 bit 一致性狀態 + 共享者列表：I/S/E），Host 1 取共享副本置 S 並記錄，Host 4 要獨佔時向 Host 1/Host 3 廣播 Back-Invalidate、收到全部確認後才轉交所有權。這是第一次把"多台獨立主機的快取一致性"放進一個記憶體裝置：GFD（Global Fabric-Attached Memory）可同時服務 4096 個獨立節點（MLD 上限 32），透過不參與各節點配置空間列舉實現規模擴張。

**PBR：面向 4096 端點的路由。** 端口基路由（Port Based Routing）放棄 CXL 2.0 的分層地址路由（交換需維護每台主機的 VH 與地址對映），改為 12-bit PID 純埠路由：邊緣埠（edge port）做**無狀態**的 HBR↔PBR 轉換（Address→PID 經 FAST 表、LD-ID→PID 經 16 深查找表、CacheID/Bus Number→PID），內部交換（spline）只按 DPID 查轉發表、完全不做地址解碼。路由表由 FM 集中配置，支援多條目的埠實現負載均衡與故障重配置——再次印證"中心控制、簡化轉發"的 CXL 哲學。ISL（交換間鏈路）需要承載 12 條對稱通道（上行/下行各 12，含獨立流控），與主機/裝置鏈路的單向上行或下行形成對比。CXL.cache 也借 CacheID 字段（4-bit）從每 root port 一個快取裝置擴展到 16 個，但主機 snoop filter 的規模仍約束其總數。

### 3.4 實測資料：延遲與頻寬的量化驗證

論文的第三部分價值在於給出可審計的數字。延遲方面（論文圖 19 的微架構拆解）：CXL 埠內部往返延遲為 **21ns（共同時鐘）/ 25ns（獨立時鐘）**，一次 CXL.cache+mem 訪問要穿過埠兩次（CPU 側 + 裝置側），加上 15ns 帶 retimer 的飛行時間，得到 **57ns 的端到端延遲增量**——與 CPU-CPU 一致性鏈路相當，且落在規範 pin-to-pin 目標（記憶體訪問 80ns、snoop 響應 50ns）之內。CXL.io 的記憶體讀延遲約 275ns（LLC miss + IOTLB hit，與 PCIe 相同）。按拓撲估算：CPU→Type 3 SLD 記憶體約 **170ns**；經一個 CXL 交換約 **250ns**；同 SMC 的兩 CPU 訊息往返約 **220ns**；跨兩個交換約 **270ns**。CPU 側 load-to-use 均 <100ns。

頻寬方面，x16 @ 32 GT/s 的原始頻寬 64 GB/s/方向、@ 64 GT/s 為 128 GB/s/方向，乘以鏈路效率（68B Flit 模式 0.924、256B/128B LO 模式 0.938——LO 模式"15 槽資料 + 1 槽開銷"的結構讓各 Flit 類型效率趨同）再扣除協議頭佔用：CXL.cache 讀約 **56.6 GB/s**（68B @ 32 GT/s）、112 GB/s（256B @ 64 GT/s）、104 GB/s（LO @ 64 GT/s）；寫約 40 GB/s（68B @ 32 GT/s，每次寫要 Req+Evict+MemWr 三個頭）、73.8 GB/s（256B/LO @ 64 GT/s）。CXL.mem 純讀約 53.5 GB/s（68B @ 32 GT/s）。論文特別強調 UIO/BI 的收益：即使 100% 訪問都觸發 Back-Invalidate 的病理情形，其鏈路效率仍優於傳統"全部繞經主機"的多 cache line 傳輸。

硬體生態方面，論文調研時點（2023 年中）：Intel Sapphire Rapids 與 Agilex7 FPGA 支援全部三協議，AMD Genoa/Bergamo 支持 CXL，ARM V2/N2/E2 宣布 CXL 2.0；Samsung 公開了 CXL 1.1 記憶體擴展器的基準資料，SK Hynix/Micron/Microchip/Astera 等宣布 Type 3 裝置，Micron 原型了 CXL 1.1 近記憶體計算裝置。論文坦承實測資料以 Intel 為主（公開資料主要來自 Intel 平台），並以"代表性效能指標"定位。

## 四、實踐：CPU 訪問 CXL 記憶體的裝置形態

協議標準定義了 CXL 裝置與主機之間的"線路語言"，但 CPU 到底以什麼形態使用這塊記憶體，取決於作業系統把這批地址空間交給誰管理。Linux 的 CXL 子系統給出了一條值得玩味的統一路徑：**無論易失還是持久，每個 CXL 記憶體 region 建立後首先以 DAX 裝置（`/dev/daxN.Y`）的形態存在，再由使用者決定"留在使用者態做 mmap"還是"轉交給核心頁分配器"**。本章基於核心 6.19 原始碼（`drivers/cxl/`、`drivers/dax/`），拆解這條路徑上的三種最終形態——System RAM、devdax、持久記憶體棧——以及各自對應的 CPU 訪問方式。前文討論的是協議層語義，本章是作業系統層語義。

### 4.1 統一入口：region 建立與 DAX 裝置

CPU 訪問 CXL 記憶體的第一步，是讓記憶體進入系統地址空間。管理員用 cxl-cli 在 root decoder 上建立 region——`cxl create-region -t ram` 或 `-t pmem`：前者對應易失記憶體（論文的 HDM-H 語義），後者對應持久記憶體。核心的 region 類型也只有這兩種（`drivers/cxl/core/region.c:618-633` 的 `mode_show`，區分 `CXL_PARTMODE_RAM` 與 `CXL_PARTMODE_PMEM`）。region 提交時，核心從 CFMWS 預留的視窗分配 Host Physical Address（`alloc_hpa()`，`drivers/cxl/core/region.c:635`）——這正是論文 4.3 節"主機軟體程式設計 HDM decoder"的核心實現。

隨後發生關鍵一步：region 進入 commit 狀態時，**`cxl_dax_region` 驅動自動為每個 region 建立 dev_dax 裝置**（`drivers/dax/cxl.c:9-33`）：以 2MB（`PMD_SIZE`）對齊、`memmap_on_memory` 預設開啟，暴露為 `/dev/daxX.Y`。這意味著 devdax 不是與 ram/pmem 並列的第三種 region 類型，而是所有 region 的"出廠形態"——核心先交出一把直接對映的鑰匙，而非自行決定記憶體歸屬。

### 4.2 形態一：System RAM——轉交給核心頁分配器

若想讓 CXL 記憶體"像普通記憶體一樣"被系統使用，執行 `daxctl reconfigure-device --mode=system-ram dax0.0`（核心動作是把該 region 的 dev_dax 繫結到 `dax_kmem` 驅動；預設將記憶體塊 online 為 movable，`--no-movable` 上 ZONE_NORMAL，`--no-online` + `daxctl online-memory` 可手動控制 online 時機；sysfs 等價路徑是 `echo dax0.0 > /sys/bus/dax/drivers/device_dax/unbind` 后 `echo dax0.0 > /sys/bus/dax/drivers/kmem/bind`），CXL 記憶體即進入記憶體熱插拔框架，成為頁分配器管理的普通記憶體。轉換由 `dev_dax_kmem_probe()` 完成（`drivers/dax/kmem.c:68`），其流程忠實體現了前文協議章的全部概念：

- **NUMA 歸屬**：取 `dev_dax->target_node`（源自 SRAT PXM/CEDT 映射），無效節點直接拒絕（`kmem.c:85-90`）——保證慢記憶體不會被混進快節點，這是論文 CDAT 屬性的落地；
- **記憶體層級（memory tier）**：`mt_calc_adistance()`（`kmem.c:92`）根據 CDAT/HMAT 距離計算該記憶體所屬的層級，供核心做層級感知的記憶體分配；
- **資源標記**：`res->flags = IORESOURCE_SYSTEM_RAM`（`kmem.c:167`）後呼叫 `add_memory_driver_managed()`（`kmem.c:177`）——"driver managed"意味著這批記憶體**明確排除在 kexec 核心之外**（memory-hotplug.rst 解釋：防止 CXL 裝置在系統重啟時被 reset 導致新核心被覆蓋）。

線上化後的行為由三處配置決定（優先順序遞減）：`CONFIG_MHP_DEFAULT_ONLINE_TYPE` 編譯項 → `memhp_default_state` 核心參數 → `/sys/devices/system/memory/auto_online_blocks`，決定記憶體塊進入 `ZONE_NORMAL`（几乎任何分配可用）還是 `ZONE_MOVABLE`（僅可遷移分配，保住未來整區熱移除的能力）。`struct folio` 描述符的來源由 `memmap_on_memory` 控制：從本塊記憶體中劃出，或從執行熱插拔 CPU 的本地 `ZONE_NORMAL` 分配——對高延遲的 CXL 記憶體池，若 folio 落在 CXL 記憶體上且被爭用，會帶來顯著效能損失。

**CPU 訪問方式**：完全透明。普通 load/store 指令，經 CPU 快取層次，協議層一致性（HDM-H）由主機保證——與本地 DDR 的唯一差異是 NUMA 距離與頻寬/延遲特徵，應用程式甚至無需感知它的存在。這是三種形態中唯一"不需要任何程序改造"的形態，也是 Tiered Memory、記憶體池化的預設選擇。

### 4.3 形態二：devdax——留在使用者態，mmap 直訪

若建立 region 后不做 online，`/dev/daxN.Y` 就保持裝置形態：使用者程式 `mmap()` 該裝置（offset 需按 2MB 對齊），把 CXL 物理頁直接對映進行程頁表。核心路徑是 `dax_mmap()`（`drivers/dax/device.c:288-305`），page fault 時建立到 CXL 記憶體的對映（`ZONE_DEVICE` 直映射；社群正在推進 vmemmap 描述符最佳化以降低大容量 DAX 的後設資料開銷，尚未合入主線）。

**與 System RAM 形態的本質差異不在 CPU 訪問路徑**——mmap 之後同樣是 load/store、同樣可快取、同樣一致性——而在於**分配與回收由誰管理**：System RAM 形態下核心頁分配器掌握所有權（malloc/free 背后是它），devdax 形態下使用者態程式碼自己決定這塊記憶體怎麼分、給誰用。它繞過了頁快取、頁分配器與檔案語義，適合"自定義記憶體池""固定大小記憶體預留"這類需要精確控制的使用場景——把 CXL 記憶體切給特定應用而非全系統。

### 4.4 形態三：持久記憶體棧——pmem 的塊裝置與檔案語義

`-t pmem` 的 region 走另一條獨立路徑：`cxl_pmem_region` 驅動（`drivers/cxl/pmem.c:375`）經 nvdimm 匯流排把 region 暴露為持久記憶體，最終由 pmem 驅動呈現為塊裝置（`pmemN`）。在塊裝置之上有三種用途：

| 用途                  | 訪問方式                                          | 適用場景                                                                                                                                |
| --------------------- | ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 普通塊裝置            | 塊 I/O（經頁快取）                                | 傳統檔案系統，不利用 DAX 能力                                                                                                           |
| fsdax（檔案系統 DAX） | 頁錯誤時檔案頁**直接映射** CXL 物理頁，繞過頁快取 | 持久記憶體的典型用法：ext2/ext4/xfs/virtiofs/erofs 五個檔案系統支援 `-o dax`（Documentation/filesystems/dax.rst），映射后 load/store 直訪 |
| 持久 devdax           | mmap 直訪                                         | 持久記憶體的裸裝置管理（同 4.3，但資料掉電不丟）                                                                                          |

fsdax 的語義與 devdax 的差異在於介面：devdax 是"一塊記憶體"（整個 region 一個檔案），fsdax 是"一個檔案系統"（文件粒度、許可權、共享、快照語義），檔案頁缺失時直接把 CXL 物理頁對映進頁表，省去頁快取這層複製——這正是 DAX（Direct Access）的名字由來。

### 4.5 決策框架：三種形態怎麼選

| 維度     | System RAM（`daxctl reconfigure-device`） | devdax（不 reconfigure）                | pmem + fsdax                        |
| -------- | ----------------------------------------- | --------------------------------------- | ----------------------------------- |
| 所有權   | 核心頁分配器                              | 使用者態程式碼                              | 檔案系統                            |
| 程序改造 | 無                                        | mmap 程式設計                               | 掛載/DAX 感知                       |
| CPU 訪問 | load/store（可快取、一致）                | load/store（mmap 后同左）               | load/store 或塊 I/O                 |
| 持久性   | 易失                                      | 易失（ram region）或持久（pmem region） | 持久                                |
| 熱移除   | 可（ZONE_MOVABLE 時）                     | 直接（未使用中）                        | 先解除安裝                              |
| 典型場景 | Tiered Memory 冷層、記憶體池化、普通擴容    | 使用者態記憶體池、精確資源切分              | 持久記憶體檔案系統、資料庫 DAX 表空間 |

選擇邏輯遵循一個簡單原則：**誰應該管理這塊記憶體？** 想讓核心全權管理 → System RAM；想自己精確控制 → devdax；需要持久化與檔案語義 → pmem。注意三種形態的底層都走同一條 CXL.mem 一致性路徑，形態差異是純軟體層的所有權劃分——這是 CXL 設計"裝置簡單、主機軟體靈活"哲學的最終體現。

### 4.6 與論文的銜接：池化願景與核心現狀

論文第 7 節的池化、共享與可組合願景，在核心中的落地進度是分層的：單機形態（本章三種）已完全成熟；**跨主機形態仍是已知缺口**——Linux CXL 子系統的成熟度地圖（Documentation/driver-api/cxl/maturity-map.rst）中，"Fabrics / G-FAM"與多主機硬體一致性共享記憶體的評分均為 [0]，而裝置池化相關能力中，LD 熱插拔（經 PCIe hotplug）為 [1] 初始可用，動態容量裝置（DCD）為 [0]（`maturity-map.rst:84,147-157`）。這正好呼應論文自己的判斷：協議就緒與部署成熟之間，隔著系統軟體的長週期演進。配套工具鏈同步演進：kmem 轉換目前由 `daxctl reconfigure-device` 承擔，2026-01 的核心 patch 系列（`cxl_sysram_region`/`cxl_dax_kmem_region` 兩級顯式繫結 + `online_type` sysfs 屬性）正在把線上化策略顯式化，預計隨新核心落地。

## 五、權衡：設計取捨與部署邊界

CXL 的每一層設計選擇都伴隨明確代價。論文對"代價"的交代堪稱誠實，這些權衡正是架構評審最值得吸收的部分。

**非對稱一致性：裝置簡單，主機買單。** 主機承擔全部對等快取跟蹤、snoop 編排與 DTLB 失效管理，裝置只實現簡化 MESI。換來的是裝置端實現門檻大幅降低、生態繁榮；代價是主機的 snoop filter 規模成為 CXL.cache 裝置數量的硬約束，且跨主機的一致性要靠記憶體裝置目錄（CXL 3.0）繼續把成本外移——一致性的負擔總是落在"離記憶體最近、最集中的那一個點"上。

**CXL vs DDR：頻寬與空閒延遲的置換。** CXL 每引腳頻寬是 DDR 的 8 倍，支援更長佈線（散熱/供電更靈活）與異構介質；但**空閒延遲約為 DDR 的兩倍**。關鍵洞察在負載延遲：CXL 的頻寬優勢使其在系統繁忙時可能反超 DDR——延遲的可感知性取決於排隊，而頻寬決定排隊。這解釋了 Tiered Memory（CXL 記憶體做冷層）為何成為主流部署形態：不是"CXL 替代 DDR"，而是"CXL 擴容量、DDR/封裝記憶體保低延遲"。論文據此推斷：最終 CXL 會成為 CPU/加速器唯一的**外部**記憶體掛載點——注意"外部"二字，片內與封裝內記憶體（含 UCIe 芯片粒）繼續承擔延遲敏感部分。

**機架級而非資料中心級。** CXL 延遲比乙太網/InfiniBand 低一個數量級，但需要專用線纜、retimer、嚴格長度約束，成本與靈活性都劣於現有網路。論文引用的財務模型顯示 **sub-rack（機架內）是 TCO 甜點**；標準化的推進可以讓 CXL 擴展到 cluster/pod 級，但**不可能取代乙太網成為資料中心級網路**。CXL 與乙太網的關係是"互連分工"而非替代：細粒度、一致性、load-store 語義走 CXL；粗粒度、任意規模、容錯走網路。

**可組合 ≠ 單一巨系統。** CXL 3.0 的 4096 端點共享記憶體描繪了一幅誘人的圖景，但論文明確潑了一盆冷水：工作負載仍會偏好區域性性、儘量少跨 CXL 鏈路——因為要最小化一致性流量與**故障爆炸半徑**。可組合系統的價值是多路複用與按需裝配，而不是把機架當一台機器。這給系統軟體提出全新課題：遠端主機引發記憶體壓力時的 QoS 保障、記憶體 Fabric 上的擁塞與故障遏制，目前 CXL 的 QoS 只覆蓋 CXL.mem 而不覆蓋 Fabric 擁塞，且不支援事務級動態多路徑——均被列為規範演進方向。

**工程層面的微觀權衡**同樣值得記取：CRC 先行 vs FEC 的 2ns 延遲博弈；LO Flit 的"半 Flit 獨立 CRC"換取的無錯路徑低延遲 vs 出錯路徑的全量累積；68B Flit 模式的寫頻寬折損（每 cache line 寫要 3 個協議頭）vs 256B Flit 的頻寬恢復。這些數字說明：互聯協議的效能天花板不是單點工程，而是負載模式、Flit 布局、排程演算法三層互動的結果。

## 六、啟示：CXL 對計算基礎設施的影響與未來方向

論文最後給出四個影響判斷，其中兩條與 AI 基礎設施直接相關，值得單獨強調。

**其一，記憶體頻寬與容量擴展是當下最確定的收益。** GPU 伺服器的記憶體牆（HBM 容量有限、DDR 頻寬見頂）在 CPU 側同樣成立：Type 3 記憶體擴展器以遠低於 DDR 通道的引腳/成本代價擴展容量，比遠端 RDMA 記憶體池的延遲低一個數量級、又比本地 DRAM 廉價；Tiered Memory 軟體棧（論文引用的 TPP、Pond 等）已經成熟到可部署。

**其二，CXL 是"機架即系統"敘事的基礎設施前提。** 論文第 3.3 節描繪的多主機共享一致記憶體、裝置直連、load-store 訊息傳遞，正是 2023 年以來"機架級單域"趨勢（如 GPU 機架的 NVL72 類比）在通用互連層面的展開：CXL 3.0 讓"多個 CPU 主機 + 共享記憶體 + 直連加速器"可以在一個交換 Fabric 內以亞微秒一致性協作。對多機推理/訓練中的細粒度同步、記憶體池化，CXL 提供了網路之外的第二個工具。

**其三，池化與可組合是雲廠商的長期紅利。** Azure（Berger 本人）與各大雲廠商的 stranding 資料是 CXL 池化最有力的論據：從按峰值配置改為按均值配置，節省的是真金白銀的記憶體成本。Berger 團隊 2023 年的設計權衡研究（Pond，論文引文 [18]）表明池化的收益在超配率高的場景最顯著。

**未來方向的清單**同樣有參考價值：記憶體控制器獨立演進（自適應重新整理、可靠性改進）；CPU 架構適配（更高記憶體延遲下的預取與緩衝策略）；系統軟體（遠端記憶體壓力下的 QoS、Fabric 擁塞控制、面向可組合性的排程）；工程層面（延遲進一步壓低、錯誤遏制與爆炸半徑管理、動態多路徑）；以及透過 UCIe retimer 引入共封裝光學，把 CXL 的物理距離延伸到 pod 級。

**從 2026 年的時點回看這篇 2023 年的綜述**：CXL 2.0 的 Type 3 裝置已進入量產伺服器，Tiered Memory 成為預設部署形態；CXL 3.0 的規格後續又迭代出 3.1/3.2，PCIe 7.0 的 128 GT/s 已在路上。論文的技術分析沒有過時——它的價值恰恰在於把三代協議的動機、機制與代價固化成了可檢索的知識，讀者不需要在規範文件中自行拼圖。對想判斷"CXL 在我的系統裡應該扮演什麼角色"的工程師，這篇論文是比任何廠商白皮書都權威的起點。
