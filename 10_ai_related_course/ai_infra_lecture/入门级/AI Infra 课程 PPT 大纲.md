## 第3頁：Token 是什麼？

**標題**: 🪙 Token：AI 經濟的基本單位
**內容**:

- **Token 的定義**
  - AI 處理文字的最小單位（約 0.7 個漢字 / 4 個英文字元，即 1 個漢字約 1-1.5 個 token）
  - 模型"思考"和"回答"都以 token 計量
  - 一次對話 = 輸入 token + 輸出 token
- **為什麼 token 是經濟單位**
  - 所有模型按 token 計費
  - 推理成本 ≈ 每 token 成本 × token 數量
  - **Token 工廠的比喻**：AI 服務商就是"token 工廠"，衡量工廠效率的唯一指標是每 token 成本
- **一個直觀數字**
  - 讀一本 10 萬字的書 ≈ 15 萬 token
  - 生成一篇 2000 字文章 ≈ 3000 token

**排版建議**:

- token 計費示意（輸入+輸出）
- 實物類比圖（書、文章 ↔ token 數量）

## 第7頁：效率革命 1：MLA——把 KV Cache 壓縮 93%

**標題**: 🪄 MLA（DeepSeek V2）：KV Cache 壓縮 93.3%
**內容**:

- **問題**：標準注意力下，KV Cache 隨序列長度線性增長
  - 長對話/長文件 → KV Cache 佔滿顯存 → 成本飆升
- **MLA 的解法**：把高維 KV 投影到低維潛在空間
  - KV 維度：4096 → 512（壓縮 8 倍）
  - KV Cache 減少 93.3%
  - 注意力品質幾乎無損失
- **行業影響**：MLA 成為 2024-2026 年主流架構（DeepSeek、GLM 等）

**排版建議**:

- 壓縮示意圖（高維 → 低維潛空間）
- KV Cache 大小對比柱狀圖

## 第8頁：效率革命 2：MoE——只激活 5.5% 的參數

**標題**: ⚡ MoE：257 個專家，只激活 6 個
**內容**:

- **問題**：模型參數越多能力越強，但每次推理都要算全部參數
- **MoE 的解法**：把模型拆成多個"專家"，每個 token 只路由到少數專家
  - DeepSeek-V3：每層 257 個專家，Top-6 激活
  - 激活參數僅佔總參數的 5.5%
  - **推理成本 ≈ 同等參數量稠密模型的 1/18**
- **2026 新進展**
  - Kimi K3：896 專家激活 16（2.8T 總參數）
  - 專家路由 + 負載均衡成為標配

**排版建議**:

- MoE 路由示意圖（token 流向少數專家）
- 激活參數 vs 總參數對比

## 第10頁：效率革命 4：KDA——Kimi K3 的線性注意力

**標題**: 🧵 Kimi K3：2.8T 參數 + 1M 上下文的開源旗艦
**內容**:

- **問題**：1M 上下文的 KV Cache 高達數百 GB——標準注意力扛不住
- **KDA（Kimi Delta Attention）的解法**：用固定大小遞推狀態替代增長 KV Cache
  - 69 層 KDA（線性注意力，O(N) 複雜度）+ 24 層 Gated MLA（全域性錨點，3:1 交替）
  - 狀態大小固定，不隨序列增長
  - 配合 AttnRes（深度注意力）：把注意力從序列軸擴展到模型深度軸
- **結果**
  - 2.8T 參數，全球最大開源權重模型
  - 1M 上下文原生支持
  - Frontend Code Arena 全球第一

**排版建議**:

- KDA + Gated MLA 混合佈局圖

## 第12頁：GPU vs CPU

**標題**: 🏭 GPU：token 工廠的機器
**內容**:

- **為什麼 AI 需要 GPU**
  - Transformer 的核心是矩陣乘法：成千上萬個數字同時相乘相加
  - CPU：4-64 核，擅長序列邏輯
  - GPU：數千核並行，每秒做千萬億次矩陣運算
- **效能對比（2026：B200）**
  - CPU（Xeon）：~1 TFLOPS（FP32）
  - GPU（B200）：~80 TFLOPS（FP32）
  - 記憶體頻寬：CPU ~400 GB/s vs GPU **8 TB/s**
- **結論**：token 工廠的產能由 GPU 決定

## 第14頁：Blackwell 深度解析

**標題**: 🔬 Blackwell：為什麼它是轉折點
**內容**:

- **三大創新**
  1. **FP4 精度**：顯存減半、吞吐翻倍
     - NVFP4：4-bit 打包，Tensor Core 內即時反量化
     - MoE 模型標配（DeepSeek-V4、GLM-5.2 均支持）
  2. **NVLink-C2C**：CPU-GPU 一體化（GB200）
     - 1.8 TB/s 雙向頻寬
     - 讓"權重解除安裝"成為現實（顯存不夠時從 CPU 記憶體非同步載入）
  3. **HBM3e 8 TB/s**：頻寬翻倍
- **實測收益（DeepSeek-V3 on GB200）**
  - 解碼吞吐：H200 的 2.2K → 10.1K tok/s（**4.6 倍**）
  - 相同負載：Decode 從 32 卡 → 8 卡
  - **每 token 硬件成本：約降 4 倍**

**排版建議**:

- FP4 vs FP8 vs FP16 精度對比

## 第15頁：CUDA 程式設計基礎

**標題**: ⚡ CUDA：token 工廠的作業系統
**內容**:

- **CUDA 是什麼**
  - NVIDIA 的程式設計平台：讓開發者直接指揮 GPU 的數千個核心
  - 所有 AI 框架（PyTorch、vLLM、SGLang）底層都跑在 CUDA 上
- **程式設計模型**
  - Host-Device：CPU 指揮，GPU 計算
  - Kernel：一段在 GPU 上並行的函式
  - 執行緒層次：Grid → Block → Thread → Warp（32 執行緒）
- **記憶體層次**
  - 全域記憶體（大、慢）→ 共享記憶體（小、快）→ 寄存器（最快）

**排版建議**:

## 第16頁：CUDA 效能最佳化

**標題**: 🚀 讓 GPU 滿載：CUDA 最佳化的核心技巧
**內容**:

- **為什麼最佳化重要**
  - GPU 很貴，滿載率決定每 token 成本
  - 典型最佳化：利用率 30% → 80%
- **核心技巧**
  - 合併記憶體訪問：連續執行緒訪問連續記憶體
  - 共享記憶體：把頻繁訪問的資料放在片上
  - 避免分支发散：warp 內執行緒走同一條路
  - 混合精度：FP16 算，FP32 累加
- **目標**
  - 理論效能利用率 >80%
  - 記憶體頻寬利用率 >70%

**排版建議**:

- 最佳化前後對比
- 效能儀表盤

  - 傳統投機解碼固定驗證視窗——所有請求一刀切
  - DSpark：由草稿模型置信度決定每個請求驗證多長
    - 數學題（容易猜）：驗證 5.24 個 token
    - 詩歌（難猜）：只驗證 2.91 個
  - 高併發下吞吐提升顯著

**排版建議**:

## 第23頁：量化：FP8 與 FP4

**標題**: 🔧 量化：把模型"瘦身"一半
**內容**:

- **原理**：模型權重從 FP16（2 位元組）→ FP8（1 位元組）→ FP4（0.5 位元組）
  - 顯存減半 → 能裝更大的模型 / 更長的上下文
  - 計算更快（小精度在 Tensor Core 上更快）
- **2026 現狀**
  - FP8：標準配置
  - **FP4（NVFP4）**：Blackwell 上 MoE 標配
    - DeepSeek-V4、GLM-5.2 均支持
    - 顯存減半、吞吐翻倍
- **代價**：精度損失——但 2026 年的量化技術損失已可忽略

**排版建議**:
