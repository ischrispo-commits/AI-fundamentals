# Token 工廠的產能怎麼算？ — 從"一天最多賣多少 token"到"使用者憑什麼不退訂"

> 面向推理叢集運營者、Token 工廠從業者與 AI 基礎設施買家。本文給出一個可落地的產能度量框架：用什麼指標回答"一天最多賣多少"、"使用者憑什麼不退訂"，以及如何用開源工具 AIPerf 把框架變成可簽字驗收的數字。所有指標只依賴概念，與具體引擎、具體部署解耦。

## 一、為什麼 Token 工廠要談"產能"

Token 工廠是把「資本 → 電力 → Token」的轉化機器。對這座工廠的經營者，有兩個問題比"模型多聰明"更接近賬本：這台機器一天最多能產出多少"賣得出去"的 token，以及每個使用者憑什麼不退訂。

注意"賣得出去"四個字。一台推理叢集的吞吐指標很多（首字延遲、出字速度、每秒請求數、每卡 token 數），但它們回答的是"機器跑多快"，不是"生意賺多少"。產能要回答的是後者：在使用者願意持續付費的前提下，一天最多能交付多少合格產出。本文用一套指標框架 + 一個開源工具（NVIDIA AIPerf）把這個問題量化。

框架本身與實現解耦：概念部分適用於任何推理叢集（vLLM、SGLang、TensorRT-LLM、託管 API 均可），工具部分負責把概念變成數字。

> AIPerf（NVIDIA，Apache 2.0）：<https://github.com/ai-dynamo/aiperf>

## 二、產能度量的三個誤區

先拆掉三個想當然，因為它們恰好是產能數字不可信的原因。

**誤區一：原始吞吐是假產能。** 不顧體驗硬灌負載，吞吐確實還能漲（排隊失控、首字延遲爆炸、成功率先崩，然後使用者流失）。那些"刷出來"的 token 對應的是流失中的使用者。原始吞吐是機器極限，用於對賬；可售賣產能必須與品質承諾繫結。

**誤區二：token 數量不是價值。** 不同模型的每 token 成本差几十倍（7B 與 70B 模型的 tokens/s 可以差一個量級），同一模型不同配置（TP/PP、量化、快取策略、部署拓撲）也不同。跨模型直接比 token 數沒有意義，**每個產能數字必須繫結模型與配置宣告**。

**誤區三：品質與產能脫節。** 只報產能、不報品質承諾，是賠本買賣（賣出去的 token 沒有承諾保障）；只報承諾、不報產能，是自欺欺人（承諾了也兌現不了）。兩個數必須一起報告，而且必須出自同一統計視窗，才能直接運算對照。

## 三、先定義"賣得出去"：SLO Goodput

產能的核心指標只有一個：

```text
SLO Goodput = 每秒「成功 且 體驗達標」的請求所產出的 output tokens
```

關鍵詞是**合規**。一個請求要計入產能，必須同時滿足：請求成功、首字延遲不超過所屬檔位上限、字間隔不超標。只有這類 token 才有人付錢，它們對應的使用者還留在產品裡。

Goodput 與原始吞吐的區別在過載時最明顯：原始吞吐可能繼續上漲，同時大量請求開始違約。原始吞吐上升而 Goodput 轉跌，就是容量見頂的訊號。

在 Goodput 之上還有兩條紀律：

1. **先宣告模型，再談產能**。產能數字必須繫結"模型 + 配置"（規模、TP/PP、量化、快取策略、部署拓撲），換任何一個變數，數字都不可比；
2. **跨模型只能換算成錢**。比較兩個模型或兩個叢集的價值時，用 `$/MTok under SLO`（單位合格 token 成本），不用 token 數。

## 四、品質承諾：使用者憑什麼不退訂

產能的"合規"部分需要一套可檢驗的品質指標。使用者體感與技術指標一一對應，全部承諾 **P99**（尾部 1% 邊界：最差的請求也基本達標，而不是平均達標）：

| 使用者體感               | 指標                 | 承諾量級（示例，按業務調整）                                |
| ---------------------- | -------------------- | ----------------------------------------------------------- |
| 點下傳送後多久開始出字 | TTFT（首字延遲）     | 按請求長度分檔承諾（排隊已含在內）                          |
| 打字機流順不順滑       | ITL（字間隔）        | P99 < 100ms                                                 |
| 出字速度               | TPOT（平均出字速度） | 跟蹤項，不參與合規判定（合規集與達標率同源，維持 TTFT+ITL） |
| 服務能不能用           | 成功率               | ≥ 99.95%                                                    |
| 整體兌現度             | 達標率（Attainment） | ≥ 99%，逐檔分別承諾                                         |

為什麼尾部要求這麼狠：Agent 任務把違約乘法放大。一個 Agent 任務序列呼叫模型幾十次，單請求 99% 達標，整條任務全程無感的機率只剩 `0.99^50 ≈ 60%`。使用者體驗看的是整條鏈，所以單步的尾巴必須極窄。

兩個口徑提醒：延遲承諾取 P99 而非平均值（平均值會把一次長卡頓攤薄）；達標率按請求長度檔位分別承諾（千字任務和十萬字任務的合理等待本不相同，整體均值會掩蓋某一檔的塌方）。

## 五、兩者關係：品質約束決定產能上限

產能與品質不是兩個獨立指標，是同一個問題的兩面：品質承諾劃定了產能的邊界。

不加約束地加壓，吞吐繼續漲，但排隊失控、首字延遲爆炸、成功率先崩，Goodput 歸零。反過來，把流量壓到品質承諾恰好守住的臨界點：

```text
可售賣產能 = 品質承諾剛被守住的極限工作點上的 Goodput
            （該點的請求到達率記作 λ_slo_max）
```

λ_slo_max 是這套框架裡最重要的一個數：它把"使用者憑什麼不退訂"（一組品質承諾）翻譯成"一天最多賣多少"（一個產能數字）。越過這個到達率，產出的都是違約 token。

一句話總結：對外賣的是一個承諾（"你的每個請求都快而穩"）；對內考核一個數字（守住承諾的前提下，每天能產出多少合格 token）。

## 六、老闆視角：換算成四個數

λ_slo_max 是工程師語言。給老闆或客戶看的，是把它換算成的四個數（按模型分行）：

| 口徑       | 公式                      | 回答什麼                               |
| ---------- | ------------------------- | -------------------------------------- |
| 單卡產能   | SLO Goodput ÷ GPU 數      | 一張卡值多少 token（同模型橫向比配置） |
| 叢集日上限 | 單卡產能 × 卡數 × 86400   | 一天最多交付多少合格輸出               |
| 日產值     | 日上限 × $/MTok under SLO | 一天最多賣出多少錢（跨模型唯一可比）   |
| 支撐業務量 | 日上限 ÷ 每任務步平均輸出 | 養得起多少次任務呼叫                   |

Input 側要拆兩個數而不是一個：每天過手的 input 總量很大，但其中命中上下文快取（prefix cache）的部分近乎免費、不需要重新計算；真正消耗 GPU 算力的是未命中部分。產能彙報必須拆開："總處理 input"是規模觀瞻，"真實重算 input"決定成本與容量。只報總量，會把真實算力消耗高估一個數量級以上。

## 七、落地：用 AIPerf 把框架變成數字

工具用 NVIDIA 開源的推理基準測試工具 AIPerf（Apache 2.0，<https://github.com/ai-dynamo/aiperf>）。它對 OpenAI 相容端點做壓測，per-request 記錄 TTFT、ITL、TPOT、輸入/輸出長度等全套指標，支持 vLLM、SGLang、TensorRT-LLM、Ollama、TGI 等引擎。它恰好覆蓋框架需要的每一項：P99 統計、併發/到達率控制、暖機與正式計量兩階段、自定義資料集、生產 trace 回放。

### 指標對映：一條命令拿到全套 P99

```bash
aiperf profile --model <model> --endpoint-type chat \
  --url <endpoint> --concurrency 5 --request-count 100 --streaming
```

（`--streaming` 必開：TTFT/ITL 依賴流式逐字計時，不開則這兩項指標缺失。）

輸出即框架所需的全部指標，且自帶 avg/min/max/p99/p90/p50：TTFT（首字延遲）、Time to Second Token、Inter Token Latency（字間隔）、Output Token Throughput Per User（出字速度）、Output Token Throughput（吞吐）、Request Throughput（每秒請求數）、輸入/輸出序列長度。對映關係零成本：AIPerf 的指標字典就是框架的指標字典。

### 負載怎麼來：合成與回放

產能數字對負載形狀極其敏感（短對話與長上下文 Agent 任務的產能差幾倍），所以負載必須貼近真實。兩條路，共用同一判定口徑：

- **合成負載**：按負載 profile 取樣生成。profile 描述鏈長（一個會話幾輪對話）、think time（工具執行/人工閱讀間隔）、輸入/輸出長度分佈（用 p50/p99 兩點擬合長尾：多數請求短、長尾很重）。適合任意強度、任意形態的探索；
- **生產 trace 回放**：用真實流量的 trace 文件（到達節奏、長度分佈、字首複用結構全部真實）。AIPerf 支持 ShareGPT、BurstGPT、Agentic coding traces 等公開資料集。對 trace 的時間戳等比縮放即可提升到達率，同一份真實負載，按不同倍數壓測。

### 三階段自適應壓測：λ_slo_max 的工程方法

逐檔加壓找 λ_slo_max 是手工活，實踐中行之有效的做法是三階段自適應：

1. **Phase A 粗掃**：到達率幾何遞增（×2 起步：0.5 → 1 → 2 → 4 → 8），每檔跑完逐檔判定 PASS/FAIL。為什麼用幾何遞增而不是等差：容量-延遲關係在臨界點附近高度非線性，几何 4–5 檔即可覆蓋 16 倍負載範圍；
2. **Phase B 二分細化**：在最後一個 PASS 與第一個 FAIL 之間二分逼近，細化臨界點；
3. **Phase C 長穩確認**：臨界檔連續跑 30–60 分钟，確認無退化。對外承諾的數字必須是長穩驗證過的檔位，短跑 PASS 只是候選。

逐檔 PASS 判定三項，閾值按叢集承諾表配置：TTFT（按 ISL 分檔）P99、ITL P99、成功率，另有樣本量門檻（有效請求不足時 P99 是噪聲，該檔判無效）。請求延遲 P99 只作體驗預算跟蹤（推理模型的端到端延遲大頭是模型自己的生成時長，屬負載行為而非容量訊號，超預算標註但不改判定）。三個判定指標的惡化順序有診斷價值：TTFT 最先惡化（過載時排隊最先變長，是最早的預警線），ITL 反映 batch 過大與 decode 搶佔，成功率最后崩，但崩了就是事故。

λ_slo_max 怎麼讀：從低到高逐檔加壓，最後一個 PASS 的檔位就是 λ_slo_max。注意取"已驗證守約的檔位"而非區間中點，對外數字必須是驗證過的。AIPerf 還內建 Adaptive Scale 模式，可以在單次執行中自動發現並維持 SLO 邊界，把這個過程自動化。

### 產出：報告按模型分行

最終報告按模型分行，每行：模型與配置宣告、承諾表、λ_slo_max、單卡產能、叢集日上限、$/MTok、日產值、品質對照（各檔實測 vs 承諾）。一個數一行，可簽字。

## 八、四步流程：一次完整的產能評估

整套方法可以收斂成四步流程：

1. **定承諾**：確定叢集服務的請求類型與 SLO 檔位（延遲分檔、成功率、達標率目標），承諾必須可檢驗、可簽字；
2. **壓測找極限**：用 AIPerf 生成/回放負載，三階段自適應加壓（粗掃 → 二分 → 長穩），觀測品質指標，找到承諾剛被守住的臨界到達率 λ_slo_max；
3. **算產能**：在 λ_slo_max 工作點上，取正式計量段的產出，計算單卡產能、叢集日上限、支撐業務量（Input 側按"過手總量 / 快取複用 / 真實重算"三口徑報告）；
4. **出報告**：按模型分行，一個數一行，可簽字驗收。

## 九、取捨與邊界

框架是清楚的，但三個邊界必須誠實標註：

**1. 品質與吞吐的此消彼長。** P99 承諾越狠，產能上限越低，產能數字永遠是一組承諾的函式。承諾檔位不是拍腦袋，是業務決策：延遲敏感的應用（交互式 Agent）比非同步批處理（離線生成）付更高的單位成本。這正是 $/MTok under SLO 存在的意義：把"承諾多狠"和"成本多高"放在同一個數里比較。

**2. 產能繫結模型與配置，拓撲是其中一環。** 前面說產能數字繫結"模型 + 配置"，這裡的配置包括部署拓撲。大模型必須切卡部署，切卡就有通訊開銷：單節點 NVLink 可以大部分隱藏通訊（接近理論產能），跨節點部署通訊無法隱藏，產能可能斷崖式下跌。同模型的產能數字，換一個拓撲就不可比，產能報告必須寫清楚拓撲。

**3. 壓測是近似。** 合成負載再貼近，也不是生產流量；生產 trace 回放縮小了差距，但 trace 快照本身會過時。另外：統計視窗要取穩定期（暖機流量不計入）；短跑 PASS 不等於長穩（30–60 分鐘無退化才可對外承諾）。產能數字應該標上"評估時點 + 負載 profile 版本 + 長穩狀態"，讓它可追溯、可複核。

最後回到開頭的問題。Token 工廠的產能不是一張卡的峰值吞吐，也不是一個模型的 benchmark 分數，它是"承諾能守住的品質下，一天最多能賣多少合格 token"這個具體的數。度量它的框架只有三條：**先宣告模型，再談產能；先承諾品質，再談上限；先長穩驗證，再對外報告。** 工具（AIPerf 這樣的開源基準）負責把這三條變成可簽字的數字，剩下的，是運營者自己的判斷。
