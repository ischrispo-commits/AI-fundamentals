# 把軌跡當狀態：推理時間 Scaling 的一個新維度

> 同一份推理軌跡、同一個模型、同一次額外前向，只因為放的位置不同，分數差了一倍：
>
> ```text
> 只給軌跡、不給原文     [T, q]       43.8
> 原文 + 軌跡，軌跡在後   [x, T, q]    43.0
> 原文 + 軌跡，軌跡在前   [T, x, q]    81.8
> ```
>
> 前兩個幾乎一樣：**材料給全了，反而沒比只給一半強**。直到位置對了，才跳到 81.8。
>
> 2026-09 | 這是 Z.ai 與清華唐傑的論文 [Trace as State: Reasoning Traces as Conditional States for Long-Context Transformers](https://arxiv.org/abs/2609.02702)（arXiv:2609.02702，2026-09-02）的結論。本文把它放在推理時間 Scaling 的譜系裡講。文中數字均已比對論文原文的 Table 2 / Table 3 / Table 6。

---

## 一、Scaling 的第三條軸

訓練側的 Scaling Laws 走過三代：Kaplan 定律說參數優先，Chinchilla 修正為參數與資料同比例增長，MoE 打破了「參數量等於激活量」的等式。這條線的問題在[另一篇](scaling_laws.md)裡展開過，這裡只說它的結局：**資料快用完了**。

Chinchilla 預言 10T 參數模型需要約 200T token，而網際網路高品質文字總量估計只有 100T–300T。與其繼續在訓練側堆料，不如換一條軸：**不 Scale 訓練，Scale 推理**。o1 之后，這條軸成了主線。

它已經長出了好幾類做法：

| 類別     | 代表                             | 多花的是什麼 |
| -------- | -------------------------------- | ------------ |
| **取樣** | self-consistency、best-of-n      | 並行跑幾份   |
| **長度** | reasoning effort、budget forcing | 思維鏈寫多長 |
| **搜索** | Tree-of-Thought、MCTS            | 搜尋樹多大   |
| **迭代** | self-refine、Re2                 | 反饋幾輪     |

四類做法的共同點是：**都在「多算」上加碼**。多采几份、多想一會、多搜几枝、多改几遍。

這篇論文問的是另一個問題。

## 二、算力花出去了，產出用足了嗎

前四類方法都在增加算力的**投入量**。但算力投進去之後會產生中間產出：推理軌跡。這份產出到目前為止只有一個用途，**被讀一遍**，當作上下文的一部分。

論文指出的是：長上下文推理裡有一個結構性的錯配。

因果注意力下，靠後出現的資訊**無法影響同一次前向傳播中已經形成的、靠前的表示**。而長上下文任務往往需要維護某種「任務狀態」：正在找的目標、待查佇列、已排除的假設。麻煩在於，這些狀態**常常是讀完材料、開始推理之後才浮現的**。

打個比方：讀完 50 萬字小說的最後一章，才被告知「請找出壞人」。前面每一頁都是不帶目標讀完的。

論文的做法是把這件事反過來：**第一遍按正常順序讀完、正常推理；把推理軌跡收起來，放到第二遍的上下文前面。**

於是第二遍讀同一份材料時，模型已經知道要找什麼了。

## 三、Trace as State

### 3.1 流程

論文把它概括成 read → compute → feedback → reread 四步：

```text
第一遍   (r_j, a_j) ~ M(· | x)         跑 n_tr 次，各得一條軌跡和一個答案
序列化   T = π(r_1, …, r_ntr)          只加分隔符和一句引導語
第二遍   (r', a') ~ M(· | [T, x, q])   帶著 T 重讀原文
```

序列化本身几乎不做加工：保留源順序，加 `<trace_start>` / `<trace_end>` 之類的分隔符，再補一句「軌跡可能有錯、請對照原文」的提示。過長的軌跡截斷到前 50,000 字符。

論文對軌跡的定位很剋制：**「任務狀態的可觀測文字代理」**，並明確說它「可能不完整、有損、或有錯」，不等同於模型內部狀態，也不等於形式化的任務條件。這個定位後面還會用到。

### 3.2 嚴格對照

這篇的實驗設計乾淨到值得單獨說。它設了一個對照組 **Trace Append**：同樣一份 T，放在上下文**后面**。

```text
TRACE AS STATE   M(· | [T, x, q])     軌跡在前
TRACE APPEND     M(· | [x, T, q])     軌跡在後
```

同一個 x、同一個 T、同一個模型，**唯一的變數是順序**。

這就把問題問得很清楚了：軌跡放前面，到底比放後面強在哪？

差別在因果注意力上。放后面，T 只能影響它之後的推理和最終回答，**改不了模型已經對 x 形成的理解**；放前面，模型是在「知道要找什麼」的前提下重讀 x 的。

### 3.3 為什麼前面比後面好

論文給了一個形式化論證。把處理器抽象成因果狀態更新器：

```text
s_i = U(s_{i-1}, c_i)        i = 1, …, n
```

任務條件 z 決定初始狀態 `s₀ = z`。同樣的序列 C、同樣的條件 z，只有順序不同：

| 順序                | 處理器何時知道該走哪條路徑 | 需要的工作記憶體                              |
| ------------------- | -------------------------- | ------------------------------------------- |
| **[z, C]** 條件在先 | 讀完 z 就知道              | **⌈b⌉ 比特**（b = log₂\|S\|，只存當前狀態） |
| **[C, z]** 條件在後 | 讀完整段序列才知道         | **⌈b·2ᵇ⌉ 比特**                             |

第二行是這麼來的：條件在後時，處理器讀完了 C，還不知道該把哪個初始狀態傳播進去，於是必須為每一個可能的 z 保留一份完整的響應檔案。S 到自身的函式共有 `|S|^|S|` 個，取對數就是 `|S|·log₂|S| = b·2^b`。

**最壞情況下，兩種順序的工作記憶體差一個指數。**

由此得到一條排序原則：**任務條件在它所指導處理的資訊之前就可用，會好用得多。**

> 需要說明的是，這是關於**抽象處理器**的結論，不是關於 Transformer 的。論文摘要自己限定得很清楚："for deterministic processors that read the input once"；正文也寫明條件狀態更新任務"are not literal models of real world long context tasks"。它提供的是排序原則的直覺，真正的證據在實驗裡。

### 3.4 實驗

三個模型，來自三家不同廠商，架構也各不相同：

| 模型                    | 論文披露的架構   | 推理檔位   | 輸入預算  |
| ----------------------- | ---------------- | ---------- | --------- |
| DeepSeek V4 Pro Preview | CSA + HCA + mHC  | max        | 1,048,576 |
| Qwen 3.7 Max            | GDN + GA         | xhigh 提示 | 983,616   |
| GLM-5.2                 | DSA + IndexCache | max        | 1,048,576 |

三個基準：**GraphWalks 256K**（長邊表上的圖狀態維護）、**MRCRv2 8-needle**（把最終請求繫結到正確的歷史問答實例）、**NUB-1M**（40–70 萬 token 長篇小說的閱讀理解）。每題 5 次重複，第二遍帶上全部 5 條軌跡。

主結果（Table 2，全部為 5 次重複的平均值，單位 %）：

| 模型                | 條件               | BFS EM / F1 | Parents EM / F1   | MRCR 256K EM / Seq | MRCR 512K EM / Seq | NUB Acc |
| ------------------- | ------------------ | ----------- | ----------------- | ------------------ | ------------------ | ------- |
| **DeepSeek V4 Pro** | 首遍               | 31.6 / 36.4 | 29.2 / 46.5       | 53.8 / 78.5        | 45.4 / 63.6        | 60.0    |
|                     | Trace Append       | 41.8 / 48.3 | 43.0 / 65.3       | 66.6 / 79.6        | 49.4 / 66.9        | 71.0    |
|                     | **Trace as State** | 58.8 / 65.9 | **81.8 / 91.3**   | 76.8 / 88.7        | 52.6 / 73.3        | 73.0    |
| **Qwen 3.7 Max**    | 首遍               | 60.0 / 68.1 | 60.8 / 87.2       | 79.8 / 83.1        | 36.2 / 43.7        | 37.0    |
|                     | Trace Append       | 60.4 / 70.4 | 71.0 / 91.7       | 84.0 / 87.1        | 40.4 / 47.4        | 49.0    |
|                     | **Trace as State** | 63.8 / 71.7 | **96.4 / 99.1**   | 88.4 / 91.3        | 46.8 / 52.5        | 51.0    |
| **GLM-5.2**         | 首遍               | 55.8 / 70.7 | 66.4 / 88.5       | 40.2 / 48.2        | 42.6 / 52.0        | 43.0    |
|                     | Trace Append       | 60.0 / 75.8 | 83.2 / 92.7       | 40.0 / 58.3        | 44.6 / 59.9        | 65.0    |

橫向 9 個指標 × 3 個模型 = 27 個組合，**Trace as State 贏下 26 個**。

唯一的例外是 GLM-5.2 的 BFS F1：75.0 對 75.8，差 0.8 個點（同一個子任務的 EM 仍是前者高）。DeepSeek V4 Pro 與 Qwen 3.7 Max 則在每一個指標上都偏好前置。

收益最大的是 GraphWalks Parents。這個子任務要求模型在解讀圖的過程中始終維護「前驅節點」這個狀態，正好是「任務狀態前置」最能幫上忙的場景。

### 3.5 消融：五個對照逐一堵死

主結果之外的替代解釋，論文用一組對照逐個排除（DeepSeek V4 Pro / GraphWalks 256K）：

| 對照               | Prompt           | BFS EM   | Parents EM | 排除了什麼           |
| ------------------ | ---------------- | -------- | ---------- | -------------------- |
| 首遍               | `[x, q]`         | 31.6     | 29.2       | —                    |
| Majority@5         | 首遍 5 次投票    | 35.0     | 31.0       | —                    |
| Oracle@5           | 首遍事後擇優     | 50.0     | 50.0       | —                    |
| Question First     | `[q, x, q]`      | 33.4     | 53.0       | 問題本身就是任務狀態 |
| Re2                | `[x, q, x, q]`   | 49.0     | 50.0       | 單純重讀有用，但不夠 |
| Answer Feedback    | `[a, x, q]`      | 35.4     | 45.4       | 只給答案不如給軌跡   |
| **Random Trace**   | `[T_rand, x, q]` | **22.4** | **14.2**   | **格式腳手架不成立** |
| Trace Only         | `[T, q]`         | 46.2     | 43.8       | 原文仍然必要         |
| Trace Append       | `[x, T, q]`      | 41.8     | 43.0       | —                    |
| **Trace as State** | `[T, x, q]`      | **58.8** | **81.8**   | —                    |

幾條值得單獨看：

**Random Trace 比不放還差**（Parents EM 14.2 對首遍 29.2）。換成別的問題的軌跡，性能直接崩掉，收益必須來自**同一個問題**的軌跡，排除了「格式對了就行」的解釋。

**Question First 一個純 prompt 重排就拿到 53.0**。這說明問題本身也是一種任務狀態，只對 Parents 這種「目標明確」的子任務有效（BFS 上只有 33.4，幾乎沒動）。

**Trace as State 超過了 Oracle@5**（Parents EM 81.8 對 50.0）。事後從 5 個首遍答案裡挑最好的，還不如帶上軌跡重讀一遍。

還有 **Trace Only 與 Trace Append 几乎打平**（43.8 對 43.0）：一個連原文都沒有，一個材料齊全，分數卻一樣。這條最能說明問題，**收益不來自材料多少，來自材料的順序。**

軌跡條數本身也是一個旋鈕：n_tr 從 1 增到 5，效能總體上升（論文原話是 generally rises），且 Trace as State 的排序優勢全程保持。

## 四、收益的構成

前面那張消融表裡藏著一個需要拆開看的事實。

DeepSeek V4 Pro 在 GraphWalks Parents 上的首遍只有 29.2% EM。一個純粹的 prompt 重排（Question First）就把它拉到 53.0。**這一段增益跟推理軌跡沒關係**，是「讓模型知道自己在找什麼」本身的價值。

真正屬於「把軌跡當作狀態」的增量，是 53.0 → 81.8。

這個拆解論文沒有做，但讀的時候心裡應該有一杆秤。

另一半是**收益與任務類型的相關性**：

| 基准               | 任務狀態形態                | DeepSeek V4 Pro 的增益 |
| ------------------ | --------------------------- | ---------------------- |
| GraphWalks Parents | 當前節點 + 前驅集合，可列舉 | **+52.6**              |
| MRCRv2 256K        | 待繫結的問答實例，較緊湊    | +23.0                  |
| NUB-1M             | 對情節的彌散理解，不可列舉  | +13.0                  |

**狀態越緊湊、越可列舉，這個方法的收益越大。** 圖任務需要一個能寫下來的「當前走到哪」，推理軌跡恰好承載得住；小說理解的狀態是彌散的，幾條軌跡寫不全。

## 五、代價與邊界

**成本結構值得拆開看。**

| DeepSeek V4 Pro / GraphWalks 256K | 首遍   | Trace as State（總計） |
| --------------------------------- | ------ | ---------------------- |
| 輸入（cached + missed）           | 257.9M | 597.4M                 |
| 輸出（含推理 token）              | 62.5M  | 90.5M                  |

輸入漲約 2.3 倍，輸出漲約 1.45 倍。**兩遍加起來一定更貴**，多出來的輸入抵不掉。

但單獨看第二遍，有個地方值得注意：**它只產出 28.0M 輸出，不到首遍 62.5M 的一半**。帶著狀態重讀之後，模型想得更少。也就是說，這個方法不是靠「想更多」換品質，恰好相反：它用一次額外的**閱讀**，換掉了模型本來要花的長篇**推理**。

（Table 6 的 Total tokens 列給出的是兩遍的合計；只比較第二遍與首遍會被誤讀成總量對比。）

**但有一項代價論文只提了一句，沒有量化**：把新生成的軌跡插到上下文最前面，會讓整個 prompt 的字首快取失效。

- 單輪任務裡這無所謂，反正只跑一次
- 多輪 Agent 里每一次都要重排，字首複用顆粒無收

而多輪 Agent 恰恰是字首快取價值最高的場景。論文在侷限裡承認了這一點（"can also reduce key–value cache reuse in multi-round settings"），也明確說沒測多輪任務。所以這篇展示的是收益側，代價側是欠測的。

**另外三處值得留意：**

- **理論與實驗之間的橋很窄。** 指數級記憶體分離是關於抽象處理器單次讀取的最壞情況結論，論文用它「引出」方法（原文用詞是 motivate），而不是「解釋」實驗結果。兩者是呼應關係。
- **消融只覆蓋一個格子。** 上面那張對照表全部來自 DeepSeek V4 Pro / GraphWalks 256K。另外兩個模型、另外兩個資料集沒有做同類對照。
- **GLM-5.2 在 MRCRv2 256K 上，Trace Append 比首遍還低**（40.0 對 40.2 EM）。論文的表述是「Trace Append 在**許多**設定上優於首遍」，用詞準確，但容易被讀成「大多數」。

## 六、它捅破的是什麼

把這篇文章放回 Scaling 的語境裡，它的位置很特別。

取樣、長度、搜索、迭代這四類，都在回答「**再多花多少算力**」。這篇問的是「**已經花掉的算力，產出該怎麼放**」。它不是在既有維度上加碼，而是開啟了另一個維度。

而且這個維度背後有一個更普遍的觀察：**模型內部的狀態是綁在位置上的，文本不是。**

hidden state、KV cache 都錨死在特定的 token 位置上，你沒法把「讀到第 10 萬個 token 時才形成的理解」搬到第 1 個 token 前面去。但推理軌跡是文字，它可以被複制、截斷、重排，搬到任何位置。

一旦承認「軌跡即狀態」，隨之而來的能力就不止於重排：

- 狀態可以**跨會話**傳遞
- 可以**跨行程**傳遞
- 甚至可以**跨模型**傳遞，不需要共享 KV cache，也不需要同一份權重

**在多智能體系統裡，這就是一個天然的交接協議。**

## 結語

論文的對照設計是它最紮實的地方：同一個 x、同一個 T、同一個模型，只改順序。正是這個設計讓結論無法用「格式」「材料多少」「模型差異」來解釋。

回到開頭那三個數字：

```text
只給軌跡、不給原文     [T, q]       43.8
原文 + 軌跡，軌跡在後   [x, T, q]    43.0
原文 + 軌跡，軌跡在前   [T, x, q]    81.8
```

材料更全，分數卻沒變；順序一換，翻了一倍。

推理時間 Scaling 到目前為止都在最佳化「算力投多少」，這篇提示了另一件事：**同樣的算力產出，還沒有被用盡。**
