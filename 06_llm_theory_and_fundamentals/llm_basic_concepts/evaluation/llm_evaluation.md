# LLM 評估體系——方法、基準與判斷力

傳統機器學習的評估有一套成熟的約定：分類看 Accuracy/F1，迴歸看 MSE，跑個 k-fold 交叉驗證，結果就基本可信。但 LLM 的輸出是自然語言——「北京的別稱」和「中國首都的別稱」指向同一個答案，token 序列卻完全不同。同一個問題換一種措辭，同一個模型可能給出相反的答案。選擇題做對了不一定代表理解，可能只是「蒙對了」。

評估 LLM 不是跑幾個 Benchmark 然後看誰分高。選錯評估方式、忽略資料汙染、把單次 Benchmark 分數當作模型能力的等價指標——任何一個環節出問題，都會造成「評測結果好看，線上效果稀爛」的錯位。本文梳理 LLM 評估的核心維度、主流方法和關鍵陷阱，幫助讀者建立對評測數字的批判性判斷力。

---

## 一、評估維度：模型能力不是單一數字

評估 LLM 首先需要回答「測什麼」。不同下游場景對模型的要求完全不同——一個數學競賽冠軍可能完全不會寫安全的 API 響應。

### 1.1 知識與推理

衡量模型「知道什麼」和「能從已知推出什麼」。MMLU 是長期使用最廣泛的「模型能力標尺」（截至 2024 年口徑；對更強的前沿模型，社群已逐步轉向 GPQA 等更難的基準），覆蓋 57 個學科的選擇題。但僅靠選擇題分數會高估模型的理解深度——MMLU Chain-of-Thought（讓模型先推理再選）比直接選擇更能反映真實推理能力，高分模型的排序也可能因此改變。

| Benchmark | 考察方向             | 題型   | 規模     |
| --------- | -------------------- | ------ | -------- |
| MMLU      | 57 學科綜合知識      | 選擇題 | ~14K 題  |
| C-Eval    | 中文綜合知識         | 選擇題 | 12,352 題 |
| HellaSwag | 常識推理（完形填空） | 選擇題 | ~10K 題  |
| ARC       | 科學推理（小初高）   | 選擇題 | ~7.8K 題 |
| BIG-Bench | 200+ 子任務綜合      | 混合   | 超大     |

### 1.2 數學與符號推理

GSM8K 是最常用的數學推理基準——8.5K 道小學數學應用題，需要逐步推理而非直接輸出答案。但 GSM8K 有一個被反覆驗證的陷阱：模型的高分可能來自「背答案」而非推理能力。GSM-Symbolic 將題目中的數字和名稱隨機化後，多數模型的分數會大幅下滑——暴露出的是記憶而非理解。

| Benchmark    | 考察方向           | 說明                                 |
| ------------ | ------------------ | ------------------------------------ |
| GSM8K        | 小學數學應用題     | 最通用的數學基準，但存在記憶化風險   |
| MATH         | 競賽級數學         | 含代數、几何、預備微積分（Precalculus）等 7 個科目，難度遠超 GSM8K |
| GSM-Symbolic | 符號隨機化的 GSM8K | 用於區分「推理」和「記憶」           |

### 1.3 程式碼能力

HumanEval 是程式碼能力的首選基準，但 pass@k 指標需要仔細解讀——它表示 k 次取樣中**至少一次**透過測試的機率，不是單次正確率：k=1 和 k=100 的差距意味着模型可能只有 60% 的機率一次寫對，但給 100 次機會很可能有一次是對的。在生產環境中，pass@1 才是體感指標。

| Benchmark     | 考察方向               | 評估方式       |
| ------------- | ---------------------- | -------------- |
| HumanEval     | Python 函式補全        | pass@k         |
| LiveCodeBench | 實時更新的程式設計題       | 防資料汙染     |
| SWE-bench     | 真實 GitHub Issue 修復 | 端到端軟體工程 |

### 1.4 對話與指令跟隨

知識與推理 Benchmark 衡量的是「模型知道什麼」，但使用者真正感受的是「模型好不好用」——這涉及到流暢度、有用性、安全性和指令跟隨的準確性。MT-Bench 用 GPT-4 評分多輪對話品質，Chatbot Arena 用真實使用者的盲評投票——後者雖有偏差，但最接近實際體驗。

## 二、評估方法：四種正規化及其內建的偏見

確定了評估維度後，下一個問題是「怎麼測」。四種方法的差異不僅是工程實現層面的，更是方法論層面的——每種方法自帶一套系統性偏見。

### 2.1 選擇題：客觀但脆弱

模型輸出每個選項的 log-likelihood，選最高的。這是最常用的方法——可復現、自動化、可大規模執行。但選擇題對 Prompt 格式極度敏感：選項用 A/B/C/D 還是 ①/②/③/④、Few-shot 示例的順序和數量、甚至選項之間的長度差異，都會顯著影響分數。這種敏感性本身就是一個訊號：選擇題測的是「模型在特定格式下的表現」，不是泛化的能力。

### 2.2 開放生成 + 規則匹配：接近真實但提取脆弱

模型自由生成答案，用正規表示式提取最終結果後再比較——常用於 GSM8K 等推理任務。但這引入了新的脆弱性：「答案為 42」「我認為結果是 42」「答案是 42.0」——三句話意思一樣，但正則能否正確提取全看規則寫得是否魯棒。

### 2.3 LLM-as-Judge：能評估品質，也自帶偏見

用 GPT-4 等強模型對生成結果打分，解決了規則匹配無法處理的主觀評價問題。但裁判模型本身存在系統性偏見：**長度偏好**（更長的回答傾向打高分）、**位置偏好**（先出現的回答有優勢）、**自身增強偏見**（裁判模型偏好自己同類模型的輸出）。MT-Bench 和 AlpacaEval 的分數需要結合這些偏見來解讀。

### 2.4 人類盲評：金標準，但不可規模化

Chatbot Arena 的 Elo 排名是當前最受關注的「使用者體感」指標——真實使用者看不到模型名稱，只對兩段回答投票。但代價也很明顯：慢、貴、不可復現，且存在標註員文化背景和偏好的影響。

**四種方法的本質權衡**：客觀的不可感（選擇題分數 ≠ 使用者體驗），可感的不客觀（LLM-as-Judge 和人類評估各有偏見）。好的評估策略不是選一種，而是用四種方法交叉驗證。

## 三、陷阱：為什麼「SOTA」經常不可信

Benchmark 分數和模型能力之間的差距，往往來自三個系統性陷阱。

### 3.1 資料汙染

訓練資料中可能包含 Benchmark 原題或高度相似的題目。模型不是在「推理」——它在「回憶」訓練資料。檢測手段包括 n-gram 重疊分析、使用模型訓練截止日期之後釋出的 Benchmark 版本，以及動態更新的基準（如 LiveCodeBench）。

### 3.2 Prompt 敏感性

同一模型在略微不同的 Prompt 下，同一 Benchmark 的分數可以相差數個百分點（具體幅度因基準與模型而異，沒有通用數字）。這意味著「分高」不等於「模型強」——可能只是「Prompt 寫得好」。好的評估應該使用多套 Prompt 模板，報告均值與方差，而非單次最高分。

### 3.3 維度錯配

用 GSM8K 證明「數學好」、用 HumanEval 證明「能用」——這是能力維度的偷換概念。GSM8K 只測小學到初中難度的應用題，HumanEval 只測簡短的函式補全。當模型聲稱在這些基準上超越人類時，需要追問：超越的是哪個維度上的人類？
