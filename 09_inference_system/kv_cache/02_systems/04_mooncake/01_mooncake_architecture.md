# Mooncake 架構概覽：以 KV Cache 為中心的高效 LLM 推理系統設計

> 本文對照 FAST 25 正式版論文 _Mooncake: A KVCache-centric Disaggregated Architecture for LLM Serving_（arXiv:2407.00079）核對。早期 arXiv v1（2024-07）與正式版存在數字口徑差異，文中已標註；引用本文數字時建議一併註明版本。

## 1. 摘要

**Mooncake** 是月之暗面（Moonshot AI）為其智慧助手 Kimi 構建的分離式 LLM 推理平台，核心是**以 KVCache 為中心的排程器（Conductor）**與**分離式全域性 KVCache 池（Mooncake Store）**，將預填充（Prefill）與解碼（Decode）叢集分離，並利用 GPU 叢集中未充分利用的 CPU、DRAM、SSD 與 NIC 資源建立 KVCache 中心化快取。

主要結果（FAST 25 正式版口徑）：

- **真實 trace 下有效請求容量提升 59%–498%**（對比基線方法，同時滿足 SLO）。早期 arXiv v1 曾報告模擬場景吞吐提升最高 525%，該數字在正式版中已移除，引用時注意版本；
- **Kimi 生產環境**：對比基於 vLLM 的舊系統，A800 叢集多處理 **115%**、H800 叢集多處理 **107%** 請求（v1 口徑為 75%，正式版已更新）；
- **全域性快取收益**：Mooncake Store 的 cache hit rate 最高達本地快取方案的 **2.36 倍**，節省最高 **48%** 的 prefill 計算時間；
- **傳輸引擎**：較現有方案快約 **2.4×** 與 **4.6×**。

核心創新點（對應論文 §3–§4）：

1. **分塊管道並行（CPP）**：長上下文預填充切分為 chunk 多節點流水處理，降低網路消耗並簡化部署，緩解跨節點 TP 的 MFU 劣化；
2. **KVCache 感知全域性排程**：Conductor 基於「字首匹配長度 → 傳輸/排隊/執行時間估計」選擇 prefill 實例，並配合基於負載的熱點自動遷移；
3. **預測性早期拒絕**：對預測無法滿足 SLO 的請求提前拒絕，避免浪費計算。

## 2. 研究背景

LLM 推理服務面臨的核心矛盾：

1. **長上下文**：可用上下文從 8k 快速增長到 128k 甚至 1M token，輸入 token 可達輸出的 10–100 倍，TTFT 最佳化成為關鍵；注意力計算量隨長度二次增長；
2. **兩階段資源畫像衝突**：Prefill 計算密集、需要高 MFU；Decode 逐 token 生成、頻寬敏感且受 TBT SLO 約束。耦合部署下兩者互相干擾；
3. **過載常態**：GPU 供給受限、彈性擴容不可行，只能主動拒絕預測無法滿足 SLO 的請求。

現有方案將預填充與解碼耦合，且快取侷限於本地 HBM/DRAM——本地 DRAM 容量只能支援理論 cache hit rate 上限的約 50%，跨會話/跨請求的字首複用大量流失。Mooncake 以 KVCache 為排程核心重構兩階段。

---

## 3. 核心架構設計

### 3.1 分離式全域性 KVCache 池（Mooncake Store）

- **資源池化**：利用叢集中未充分利用的 CPU、DRAM、SSD 與 NIC 資源建立分離式 KVCache 池，跨會話、跨請求共享字首；
- **塊狀儲存與鏈式雜湊**：所有 KVCache 以分頁塊儲存，塊大小由模型規模與最優網路傳輸大小決定，**典型範圍 16–512 token**；每個塊的雜湊鍵由自身內容與字首塊的雜湊共同決定，因此字首命中必須從開頭連續匹配；
- **驅逐策略**：采用 **LRU**（被活躍請求引用的塊不可驅逐）；
- **全局 vs 本地**：實驗中全域性快取的 cache hit rate 最高為本地方案的 **2.36 倍**，本地 DRAM 容量只能支撐理論命中率上限的約 50%——這是全域性池設計的核心依據。

- **傳輸引擎**：基於 RDMA 的高速 KVCache 傳輸，實測約為現有方案的 **2.4×** 與 **4.6×**；傳輸與增量 prefill 計算非同步重疊執行。

### 3.2 雙階段分離排程

| 維度                 | 預填充叢集（P）           | 解碼叢集（D）                      |
| -------------------- | ------------------------- | ---------------------------------- |
| 最佳化目標             | 最大化 MFU、滿足 TTFT SLO | 滿足 TBT SLO                       |
| 長上下文並行         | 分塊管道並行（CPP）       | —                                  |
| 批處理               | chunk 粒度流水            | 連續批處理                         |
| SLO 閾值（實驗設定） | TTFT ≤ 30 s               | TBT ≤ 100 / 200 / 300 ms（按場景） |

實驗叢集配置：16 節點 × 8×A800（LLaMA3-70B，單 token KVCache 約 320 KB）。

**CPP 機制**：將 prefill 叢集每 X 個節點組成一個流水線 prefill 節點組，請求輸入切分為多個 chunk（閾值按 GPU 算力選取，**典型大於 1000 token**），不同 chunk 由組內不同節點同時處理。相比跨節點 TP（每層兩次昂貴的 RDMA all-reduce）與傳統序列並行（SP），CPP 降低網路消耗並提升 MFU。

## 4. 關鍵最佳化技術

### 4.1 KVCache 感知全域性排程（Algorithm 1）

對每個新請求，Conductor 的排程流程：

1. 計算請求的 prefix hash，與各 prefill 實例的快取鍵逐一比對，得到各實例的**字首匹配長度**；
2. 對每個實例估計 `Ttransfer + Tqueue + Tprefill`（基於離線資料擬合的多項式預測模型），選 **TTFT 估計值最小**的實例；
3. 當最佳匹配實例負載過高（超過 `kvcache_balancing_threshold`）時，允許向次優實例遷移快取——**若估計的額外 prefill 時間短於快取傳輸時間，則寧可重算**；
4. 准入判斷：估計 TTFT 超過 TTFT SLO、或 TBT 超過 TBT SLO 的請求被**主動拒絕**。

排程演算法的實測收益（conversation trace，16 節點 8×A800）：全局 cache-aware 排程相比本地 cache-aware 排程，平均 TTFT **再降 14%**；並優於 random 與 load-balancing 排程。

**熱點遷移**：論文明確否決了「預測未來使用量」的方案（負載高度動態、無法準確預測），改用啟發式自動熱點遷移提升快取負載均衡。

### 4.2 預測性早期拒絕

由於 GPU 供給彈性受限，Mooncake 對**預測無法滿足 SLO 的請求**提前拒絕，避免無效 prefill 計算。預測基於請求特徵（輸入/輸出長度等）結合當前負載，輸出長度預測器用於判斷請求能否在 SLO 內完成。

## 5. 實驗驗證

### 5.1 工作負載（論文 Table 2）

其中 Conversation 負載最長請求達 128k token；有效請求定義為 TTFT 與 TBT 均低於各自閾值的請求。

### 5.2 主要結果

| 工作負載                   | Mooncake 有效請求容量提升    |
| -------------------------- | ---------------------------- |
| Conversation（真實 trace） | 最高 **+498%**               |
| Tool&Agent（真實 trace）   | **+64%**                     |
| 真實 trace 整體範圍        | **59%–498%**（對比基線方法） |

- **基線**：vLLM、vLLM + prefix caching、vLLM + chunked prefill（各 16 節點）；
- **Store 消融**：全域性快取使 cache hit rate 最高達本地方案的 **2.36 倍**，prefill 計算時間節省最高 **48%**；
- **傳輸引擎消融**：較現有方案快約 **2.4×** 與 **4.6×**；
- **生產環境**：Kimi 在 A800/H800 叢集分別多處理 **115%** / **107%** 請求（對比舊 vLLM 系統）；
- **版本差異**：arXiv v1 曾報告模擬場景（合成負載）吞吐提升最高 525%，FAST 正式版以真實 trace 的 59%–498% 為準。

## 6. 工程實踐啟示

1. **儲存優先原則**：長上下文場景下 KVCache 是顯存與網路的主要瓶頸。Mooncake 以 KVCache 為中心，優先利用 CPU/DRAM/SSD/NIC 的閒置資源建立全域性池，用「全局命中率 2.36× 於本地」的實測資料支撐了資源池化的決策。

2. **解耦排程：排程即估計時間**。Conductor 的排程不是抽象的評分函式，而是把「換一個實例」拆成傳輸、排隊、執行三段可估計的時間再求和取最小，並用同一套估計值做 SLO 准入。這個「排程決策 = 時間估計」的思路可推廣到其他狀態重用場景。

3. **預測的邊界**：論文對兩種預測給出了不同答案——**輸出長度可預測**（用於早期拒絕），**未來快取使用量不可預測**（因此熱點遷移用啟發式而非預測模型）。什麼時候該用預測、什麼時候該放棄預測，論文給出了一個乾淨的對照。

## 7. 延伸討論（本文觀點，非論文內容）

論文字身未展開以下方向；這裡是本倉基於架構特徵的延伸思考，不代表 Mooncake 團隊立場：

1. **異構加速器**：預填充/解碼分離後，兩類叢集可以選用不同硬體畫像（算力型 vs 頻寬型），論文未討論異構配置；
2. **更遠的分層**：Store 已利用 DRAM/SSD/NIC，CXL 記憶體池等新介質與該架構的適配是開放問題；
3. **跨叢集/多租**：跨地域快取共享涉及隱私與資料駐留，論文未涉及。

---

## 8. 技術價值總結

1. **架構**：首個在大規模生產環境驗證「分布式 KVCache 池跨會話共享」價值的系統（論文自述為同類首個）；
2. **方法**：把排程問題還原為可估計的時間分解（傳輸/排隊/執行），並區分「可預測」與「不可預測」分別設計機制；
3. **驗證**：真實 trace、生產叢集（數千節點、日處理超千億 token）與消融實驗齊備，結論的工程可信度較高。
