# 訓練不穩，可能是推理引擎的鍋：Miles 的三條對齊路線

> 2026-09 | 基於 [radixark/miles](https://github.com/radixark/miles) 原始碼（HEAD `7daba3a`，2026-09-14）與其 arXiv 技術報告（[2609.08368](https://arxiv.org/abs/2609.08368)）逐條核對。文中原始碼引用以 `file:line` 標註；效能數字全部為**廠商口徑**，截至寫作時**沒有任何第三方獨立復現**。

## 一、同一份權重，兩個機率

把一個訓練好的模型權重同時交給兩個系統（SGLang 做推理、Megatron 做訓練），讓它們對同一個 token 序列各算一遍 log-probability，得到的數字不會一樣。

這不是 bug。兩邊用不同的 kernel、不同的數值精度、不同的歸約順序做同一件事，而浮點加法不滿足結合律，結果自然不同。

問題在於，RL 後訓練要求它們相同。

RL 的每一步都要算這樣一個比值：當前策略生成某個 token 的概率，除以生成它時所用策略的機率。這正是 PPO 一類的演算法的立足點：只有分子分母出自同一個策略，這個比值才是無偏的。而 rollout 是 SGLang 產的、概率是 Megatron 重算的，兩者只要對不上，**策略梯度的方向就不再是你以為的那個方向**。

Miles 的文件把這件事寫成了一句話：

> A common failure mode in MoE RL is precision drift between training and inference. Pipelines that train in BF16 and serve in FP8 accumulate per-layer numerical disagreement, which compounds into divergent log-probabilities and gradients pointing in unintended directions.

（`docs/advanced/low-precision.md`）

先看這個差異的真實量級。Miles 技術報告裡的 GLM-5.2 參考執行，訓練與推理對同一批取樣 token 的 log-prob 分歧，100 步均值是 **0.0369**；LMSYS 博客里 DeepSeek-V4.1 那次執行，平均絕對差是 **0.017–0.025 nats**。

兩個數字都不大，也都沒有到 0。後面會看到，**「到 0」是有專門做法的，而那套做法目前還只能用在很小的模型上**。

## 二、裂縫從四個地方來

要理解「對齊」為什麼會成為一個工程問題，先得知道不一致是怎麼攢出來的。

**精度路徑不同。** 訓練側常跑 BF16，推理側為了吞吐跑 FP8 甚至 FP4。同一個權重，一邊按 BF16 舍入、一邊按 FP8 舍入，每一層就多出一點偏差；幾十層疊上去，log-prob 的差就出來了。Miles 文件用的詞是「compounds」。

**kernel 實現不同。** 矩陣乘法在 GPU 上怎麼切塊、怎麼累加、用哪條指令路徑，不同實現給出的有效數字不同。Miles 在實現逐位對齊時踩到的正是這一層：它必須讓兩側都走 FlashAttention 3，因為只有這個後端在 prefill 與 decode 之間是逐位相等的。

**batch 組成會影響結果。** 大多數 kernel 的輸出依賴 batch 裡的其他樣本，歸約順序隨 batch 形狀變。這類 kernel 叫 batch-variant，是數值對齊的前提性障礙，Miles 用的是 Thinking Machines Lab 開源的那組 batch-invariant 算子。

**MoE 的路由可能不同。** 專家路由靠 Top-k 打分，一旦出現分數並列，兩個系統可能選中不同的專家。走錯專家意味著**換了一條計算路徑**。

前三條是數值問題，第四條是結構問題，處理方式也不一樣。

## 三、路線一：把差異消掉

Miles 最常見的那條路，目標定得很絕對：

> True on-policy ensures that the log probs generated by inference engine (SGLang) is strictly equal to the one generated by the training Engine.

（`examples/infra_features/true_on_policy/README.md:3`）

實現思路是讓**訓練與推理的每一個操作都逐位相等**（bitwise equal）：

- **注意力**：兩側都用 FlashAttention 3，因為它在 prefill 與 decode 之間逐位相等；
- **GEMM**：用 DeepGEMM 保吞吐，同時靠它對 tensor core 指令的選擇保持一致性；
- **batch-invariant 算子**：逐位對齊的前提，采用 Thinking Machines Lab 的開源實現；
- **`torch.compile`**：把大量小 kernel 合併，減少逐位對齊需要覆蓋的面。

再往下是磨細節：對齊兩側的 op dtype、替換 Megatron 側 TE 的 fused 實現、關掉 fused rotary embedding、SGLang 開 deterministic inference、把 cuBLAS/TE/NCCL 都配成確定性、rollout 側改用一次 prefill pass 重新打分而不是回報 decode kernel 的 log-prob（`miles/true_on_policy/config.py:204-207`）。

**驗收標準是一個數**：wandb 里的 `train/train_rollout_logprob_abs_diff` 必須**嚴格等於 0**。這個指標在訓練迴圈裡實時算並上報（`miles/backends/training_utils/loss_hub/losses.py:340-374`），CI 裡的斷言用的是**無容差的 Python `==`**：

```python
# miles/backends/training_utils/log_utils.py:267-302
if args.ci_test and args.true_on_policy_mode and not args.ci_disable_logprobs_checker:
    assert log_dict["log_probs"] == log_dict["rollout_log_probs"], (
        f"CI check failed: true_on_policy_mode is enabled, but log_probs ...")
```

同一個檔案裡其他檢查都留了餘地：訓練側與參考模型之間 `1e-8`，訓練側與推理引擎之間 `0.03`。唯獨這一條不留。**「逐位對齊」在這裡是會掛 CI 的斷言。**

### 代價，以及它現在能覆蓋多遠

代價很直接：確定性 kernel 放棄一部分最佳化空間，**rollout 會變慢**。Miles 官方示例的結論是「rollout time shows an acceptable slowdown」（同 README），但沒給具體百分比。

更硬的邊界在程式碼裡：

**第一，只有 FSDP 后端支持。** Megatron 是 Miles 的預設後端、也是萬億參數級唯一現實的選擇，而它直接拋異常：

```python
# miles/backends/megatron_utils/arguments.py:14-20
def set_default_megatron_args(args):
    if getattr(args, "true_on_policy_mode", False):
        raise NotImplementedError(
            "--true-on-policy-mode is not supported on the megatron backend with this Megatron "
            "version; support lands in a follow-up PR. Use --train-backend fsdp for true-on-policy."
        )
```

**第二，只有 Qwen3 dense 一族註冊了對齊契約。** 啟用它的前提是存在對應模型族的 parity contract：

```python
# miles/true_on_policy/schema.py:26-34
QWEN3_DENSE_TRUE_ON_POLICY_V1_SCHEMA = TrueOnPolicyContractSchema(
    name="qwen3_dense_true_on_policy_v1",
    model_family="qwen3_dense",
    logprob_contract="sglang_prefill",
    sglang_attention_backend="fa3",
    fsdp_attention_implementation="flash_attention_3",
    disable_megatron_sequence_parallel=True,
)
```

超出已註冊的 profile 直接拒絕啟動。也就是說，**逐位對齊目前是「小模型 + FSDP + Qwen3 dense」的可用路徑**，不是通用能力。

## 四、路線二：讓兩側走同一條量化路徑

逐位對齊很難推到大規模，Miles 於是做了第二條路：不追求「消除差異」，而是讓 rollout 和 trainer 的**前向用同一套量化邏輯**。既然兩側都在做同樣精度的舍入，偏差就不會單向累積。

這條路的成品是三種端到端低精度配方：

| 格式                            | 塊佈局                         | 硬件               | 成熟度 |
|---------------------------------|--------------------------------|--------------------|--------|
| FP8 block-wise（DeepSeek 風格） | 128×128，FP32 scale            | Hopper + Blackwell | 已可用 |
| MXFP8                           | 1×32，UE8M0 scale              | 僅 Blackwell       | Beta   |
| NVFP4（E2M1）                   | 1×16，兩級 scale（FP8 + FP32） | 僅 Blackwell       | Beta   |

**關鍵不在於選了哪種格式，而在於契約覆蓋了整條鏈路**：checkpoint 轉換、trainer 前向、SGLang rollout、線上權重匯出，四個階段必須共用同一套量化規則；宣告為高精度的張量在這四段裡必須一致地保持高精度。

Miles 把這件事做到了量化器一級：**FlashInfer（推理側）與 TransformerEngine（訓練側）的量化器對齊到同一個 bit-level contract**，單元測試對參考實現做逐位元組校驗。這背後是一個很容易踩的坑：

> serving 環境預設會在 FP4 量化路徑上開 fast math。This is a reasonable serving default, but RL weight updates benefit from exact agreement with the training-side quantizer.

所以 RL 配方反過來把 fast math 關掉（`FLASHINFER_DISABLE_FP4_QUANT_FAST_MATH=1`）。**推理側為了吞吐開的最佳化，在這裡必須為訓練側的一致性讓路。**

同一條邏輯還體現在 NVFP4 配方的取舍上。NVFP4 預訓練會用隨機舍入（SR）和隨機 Hadamard 變換（RHT）當穩定器，RL 配方把兩者都去掉，理由是量化噪聲必須壓得比真實更新訊號更低，否則會把脆弱能力直接覆蓋掉，改為按 token 線上算 FP32 scale。

### 一條可以直接用的經驗結論

Miles 試了按層把一部分權重留在 BF16，結論很具體：**保留最后 15% 的層用 BF16，能明顯降低訓練-推理偏差、穩定梯度；而保留最前面的層沒有幫助。**

另一條同樣實用：MLA 結構裡有幾個投影張量（`kv_b_proj` 以及 absorbed 的 `k_up_proj` / `v_up_proj`）要留在 BF16，因為 absorbed 與非 absorbed 模式的收縮軸不同，而 MXFP8 的塊是一維的，套不上。

## 五、路線三：消不掉就修

前面兩條都要付代價：一條要讓 rollout 變慢、還只支援小模型，一條要上 Blackwell。所以在更多場景下，Miles 走的是第三條：**接受差異存在，然后修正它**。

修正分兩個層次。

### 5.1 先修結構性的：R3 重放專家路由

MoE 的路由不一致不是數值噪聲，是走錯路徑，重要性取樣修正不了。Miles 的做法（`--use-rollout-routing-replay`）是：**讓 SGLang 在生成時把選中的專家一併返回，訓練前向時直接回放，跳過自己的 Top-k gating**。

rollout 側開啟 `enable_return_routed_experts`（`miles/backends/sglang_utils/sglang_engine.py:133-136`），返回的張量形狀是 `(num_tokens-1, num_layers, moe_router_topk)`、int32（`miles/utils/types.py:99-104`）。訓練側用一個雙遊標的回放緩衝消費它：

```python
# miles/utils/replay_base.py:28-41
def pop_forward(self) -> torch.Tensor:
    top_indices = self.top_indices_list[self.forward_index]
    self.forward_index += 1
    return top_indices

def pop_backward(self) -> torch.Tensor:
    top_indices = self.top_indices_list[self.backward_index]
    self.backward_index += 1
    return top_indices
```

兩個獨立遊標是為了應對激活重算：同一批路由要被前向和反向各消費一次。

**開銷是明碼標價的**：每個 routing 張量佔 `(num_tokens − 1) × layers × top_k × 4` 位元組。32K token、60 層、`top_k = 8` 的序列，**每條軌跡約 60 MB**。所以它不是無腦開的。文件明確列出什麼時候不需要 R3：模型是 dense 的，或者已經用 TIS 把 off-policy 項遮蔽掉了。

### 5.2 再修數值殘餘：TIS

數值層面消不掉的殘餘偏差，用截斷重要性取樣兜底。Miles 內建的實現很短：

```python
# miles/backends/training_utils/loss_hub/corrections.py:7-32
def vanilla_tis_function(...):
    """Truncated importance sampling: clamp `exp(train - rollout)` to
    `[tis_clip_low, tis_clip]` and multiply into `pg_loss`."""
    tis = torch.exp(old_log_probs - rollout_log_probs)
    tis_weights = torch.clamp(tis, min=args.tis_clip_low, max=args.tis_clip)
    pg_loss = pg_loss * tis_weights
```

思路是給每個 token 的比值算一個權重，再把它夾在區間裡：偏差大的樣本不被完全信任，也不被完全丟棄。預設上界是 2.0。需要更細的策略時，可以掛自定義函式（`--custom-tis-function-path`），示例目錄裡給了一套帶 12 個監控指標的 MIS 實現。

**非同步 RL 裡這個修正不是可選項。** Miles 在啟動時強制要求顯式選擇行為策略：

```python
# miles/utils/arguments.py:3696-3714
def validate_async_off_policy_correction(args) -> None:
    """Require an explicit behavior-policy choice for async PPO training."""
    assert args.use_rollout_logprobs or args.use_tis or args.keep_old_actor, (...)
```

因為非同步 rollout 天然跨多個權重版本，樣本本來就不是嚴格 on-policy 的，必須說清楚用哪種方式處理。

## 六、這三條路各自走到哪了

把邊界收攏一下。

**逐位對齊（路線一）的適用範圍最窄。** FSDP 后端 + Qwen3 dense + 0.6B/4B 兩個 profile，超出就拒絕啟動。官方示例的 README 里那句「Potentially scale it to larger scale models if it is proven to be effective」，寫在 Future Works 一節。

**大模型上跑的都不是路線一。** GLM-5.2 那次執行的 log-prob 分歧是 0.0369，V4.1 那次是 0.017–0.025 nats，都不是 0。這兩個數字來自 Miles 自己的參考執行，說明**在萬億參數規模上，走的是「對齊 + 修正」而不是「消除」**。

**DeepSeek-V4.1 在 Miles 的公開程式碼裡不存在。** 倉庫裡有一份 225 行的 V4.1 訓練側文件，寫明瞭 Megatron 插件位置、模型定義、啟動指令碼，甚至給了 checkpoint 轉換命令，但它引用的 `miles_plugins/models/deepseek_v41/`、`scripts/models/deepseek-v4.1.py`、`scripts/run_deepseek_v41.py`、`tools/dsv41_cut_cast.py` **全部不存在**，全倉 `engram` 相關檔案為 0，`v41` 在程式碼目錄下零命中。文件自己還寫著那個 cast 工具「is kept with the bring-up scripts」。

也就是說，LMSYS 博客里描述的 V4.1 集成，**從公開倉庫既無法復現也無法驗證**。這在開源系統軟體裡並不罕見，文件先行、程式碼滯後，但它決定了我們能把哪些說法當一手證據。

**沒有獨立驗證。** 截至 2026-09-14，沒有找到任何第三方復現或獨立基準。所有效能數字（步時、權重同步加速比、顯存降幅、reward 曲線）無一例外來自 RadixArk 自己的執行，論文也自陳「some measurements come from one configuration rather than many」。

順帶一提，Miles 自己的文件有四處引用了不存在的檔案。其中包括 `miles/ray/train/actor_factory.py`，本文第四節引用的那份低精度文件，正是引用它的兩處之一。這份文件的機制描述可信（能在原始碼裡對上），但**具體路徑引用要自己核**。

## 七、為什麼這對做推理的人重要

過去幾年，「推理引擎怎麼選 kernel」被當成一個純吞吐問題：哪個後端快、哪條路徑省顯存。這篇材料給出的是另一面。

**推理引擎的每一次數值選擇，都是上游訓練的輸入。**

具體地：

- 推理側為吞吐預設開啟的 fast math，會讓 RL 的權重更新失去與訓練側量化器的精確一致，所以 RL 配方得把它關掉；
- 推理側選哪個注意力後端，決定了訓練側能不能做逐位對齊：FA3 正是因為它在 prefill 與 decode 之間逐位相等才被選中；
- 推理側的精度格式（FP8 / MXFP8 / NVFP4）不再是推理單方面的決定，而要和 trainer 的量化規則籤一份覆蓋四個階段的契約。

Miles 之所以把 SGLang 和 Megatron 縫在一起，一部分原因就在這：**這兩個系統的一致性，是它自己的正確性問題，不是別人的。**
