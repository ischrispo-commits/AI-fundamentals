# AI Agent 基礎設施——三個決定性層次：工具、資料、編排

> **原文：** <https://www.madrona.com/ai-agent-infrastructure-three-layers-tools-data-orchestration/>
> 2025-2-28 by Jon Turow

想象一家初創公司，20 人的團隊能夠在不到兩年的時間內創造 1 億美元的年經常性收入（ARR）。這不是未來主義的幻想——這是 AI 驅動增長的現實寫照。像 **Cursor**、**Bolt**、**Lovable** 和 **Mercor** 這樣的公司正在打破傳統的擴展規則，證明了配備智慧 Agent 的精簡團隊可以顛覆整個行業。

這揭示了初創公司動態的轉變。創始人不再受制於人員數量或傳統的開發週期。隨著 AI Agent 從早期成功轉向成為現代軟體的基礎組成部分，它們正在推動基礎設施需求的轉變。

這種轉變遵循著一個熟悉的模式：隨著新應用的出現，它們推動現有基礎設施的極限，創造對新能力的需求。反過來，基礎設施的進步又釋放了更強大的應用，推動下一波創新浪潮。AI Agent 也不例外——它們的快速採用正在重塑軟體的構建方式和支援它的基礎設施。

對於創始人來說，這帶來了巨大的機遇：構建 AI 原生基礎設施——涵蓋工具、資料和編排——為下一波智慧應用提供動力。

在這個新時代，每個創始人都面臨著一個關鍵選擇：適應 AI 的變革力量，或者冒著落後的風險。Agent 採用的激增不僅僅是一個趨勢——它是對軟體如何構建、部署和擴展的根本性重新想象。

## 從效率到基礎設施：更深層的訊號

這不僅僅是關於高效增長——這種轉變標誌著更深層的東西。隨著成功 Agent 應用的清晰模式逐漸顯現，創始人們正在急於擁抱和擴展有效的方法。這種 Agent 採用的激增對支援這些應用的基礎設施層提出了新的要求。

我們從 2024 年 6 月就開始追蹤這種演變，當時我們寫了關於《[AI Agent 基礎設施的崛起](02_the-rise-of-ai-agent-infrastructure.md)》的文章。那時，這個領域還很稀疏，主要由 DIY 解決方案主導，因為開發者優先考慮靈活性來試驗不同的方法。有一大批新公司在為 Agent 的未來狀態構建基礎設施，但這些公司面臨著一個移動的目標。

今天，這種情況已經發生了戲劇性的變化。證據無處不在：**無伺服器 Postgres 提供商 Neon** 報告稱，AI Agent 現在在其平台上建立資料庫的速度是人類開發者的 4 倍以上，這加速了 Neon 的整體指標。

![Neon 增長指標](https://www.madrona.com/wp-content/uploads/2025/02/Picture1.jpg)

專門的 AI Agent 基礎設施元件如 **Browserbase** 也看到了類似的加速。例如，**Browserbase 的 Stagehand UI 自動化庫**最近突破了每月 50 萬次 npm 安裝。

![Browserbase npm 安裝量](https://www.madrona.com/wp-content/uploads/2025/02/Picture2.jpg)

這些不僅僅是增長指標——它們是軟體構建和部署方式根本性轉變的訊號。這種轉變為 Agent 應用和支援它們的基礎設施都帶來了機遇。與"**當有市場地圖時，已經太晚了**"的老話相反，我們看到 2025 年成立的公司已經在這個領域獲得了顯著的牽引力。底層能力和模式發展如此迅速，新進入者可以快速識別和解決新興需求。

## 從實驗到清晰模式

一年前，Agent 開發的特點是大量的實驗。開發者主要從零開始構建，優先考慮靈活性，以便在尋找獲勝方法時進行調整。今天，情況發生了戲劇性的變化。多個可重複的模式已經出現，聰明的創始人正在急於擁抱和擴展有效的方法。

這些模式建立在我們 1 月份對 Agent 領域分析（[AI agents are stuck in first gear — but 2025 will change that](https://www.madrona.com/ai-agents-are-stuck-in-first-gear-but-2025-will-change-that/)）的基礎上，顯示了一套通用 Agent 模式正在顯現：

- **下一代 Copilot** 是上下文感知的助手，主動協助複雜任務，以 **Bolt.new**、**AirOps** 和 **Colimit** 為代表。
- **團隊成員 Agent**，如 **Ravenna**、**Sailplane** 和 **Basepilot**，更進一步，自主推動多步驟工作流程。
- **Agent 組織** 引入協作系統，多個專門的 Agent 協同工作，如 **Aaru** 的機率模擬。
- 下一個類別，**Agent 即服務**，提供專門的 Agent 能力作為面向開發者的服務，而不是面向使用者的產品。

所有這些都對基礎設施堆疊產生了影響。

## 基礎設施堆疊的出現：三個決定性層次

隨著 Agent 模式的固化，AI Agent 基礎設施堆疊的三個層次已經成為特別具有決定性的：**工具**、**資料**和**編排**。每個層次都看到激烈的競爭，因為提供商競相解決與傳統 SaaS 基礎設施根本不同的 Agent 特定挑戰。

### （一）工具層：讓 Agent 具備能力

工具層經歷了最戲劇性的擴展，反映了 Agent 互動日益增長的複雜性。關鍵戰場包括：

#### 瀏覽器基礎設施和 UI 自動化

Agent 越來越需要與視覺化網路互動——不僅僅是 API。像 **Browserbase**、**Lightpanda** 和 **Browserless** 這樣的公司正在構建使這成為可能的基礎設施，而像 **Stagehand** 這樣的專門服務為常見模式提供更高階別的抽象。

#### 身份驗證和安全

當 Agent 代表使用者行動時，身份驗證和安全呈現出新的維度。像 **Clerk**、**Anon** 和 **Statics.ai** 這樣的公司正在開創"**Agent 身份驗證**"——以 Agent 原生方式管理許可權、憑據和安全。

#### 工具發現和整合

正如 **Akash Bajwa** 最近評論的，**Anthropic** 的**模型上下文協議**（`Model Context Protocol`，MCP）正在成為潛在的"**AI Agent 的 TCP/IP**"，為 Agent 發現和與工具互動提供標準化方式，同時保持上下文。像 **Stripe**、**Neo4j** 和 **Cloudflare** 這樣的主要參與者已經提供 MCP 伺服器，表明這可能成為工具整合的關鍵標準。

像 **Composio** 和 **Arcade.dev** 這樣的公司正在這些協議之上構建抽象層。**Composio** 提供與 **Gmail** 和 **Linear** 等流行應用的 `MCP` 相容訪問，透過 `TypeScript` 和 `Python SDK` 為開發者提供標準化介面。同時，**Arcade.dev** 透過與 **OpenAI** 規範相容的統一 API 層簡化身份驗證和工具管理。

這種多層方法至關重要，因為它解決了不同的開發者需求。基礎設施團隊可以直接針對 `MCP` 等協議構建，而應用開發者可以利用 **Composio** 或 **Arcade.dev** 等託管解決方案。這些方法不是相互排斥的；相反，它們可以共存並相互補充，最終加速 Agent 驅動應用的採用。

今天，發現 Agent 就緒工具仍然經常依賴口碑傳播，感覺很像發現 **Discord** 伺服器的早期階段。但標準化協議和託管整合層的結合表明我們正在朝著更結構化的發現機制發展。

### （二）資料層：大規模記憶體

資料層說明了傳統基礎設施必須如何為 Agent 工作負載而演進。**Neon** 的經驗很有啟發性。如上所述，AI Agent 現在以人類開發者 4 倍的速度在 **Neon** 上建立資料庫，推動了對即時配置、自動擴展和隔離環境的新要求。

當 **Create.xyz** 在 **Neon** 之上推出其開發者 Agent 時，Create 在短短 36 小時內建立了 `20,000` 個新資料庫。終端使用者只是描述了他們想要構建的東西——"構建一個使用 AI 對申請進行排名的招聘網站"或"建立一個自動生成 SEO 後設資料的內容管理系統"——Agent 就會自動配置必要的資料庫基礎設施。

這種模式在整個資料層重複出現：

- **向量資料庫** 如 **Pinecone**、**Weaviate** 和 **Qdrant** 正在最佳化 Agent 記憶體和檢索模式
- **圖資料庫** 如 **Neo4j** 正在為 Agent 推理和關係對映提供專門的功能
- **時間序列資料庫** 正在適應 Agent 活動跟蹤和效能監控

關鍵的區別在於 Agent 如何使用資料。與傳統應用不同，Agent 需要：

- **動態模式演化**，因為它們學習和適應
- **高頻讀寫模式**，用於實時決策
- **複雜的查詢模式**，結合結構化和非結構化資料

### （三）編排層：協調複雜性

編排層可能是最複雜的，因為它必須管理 Agent 行為、工作流程和互動的複雜性。關鍵元件包括：

#### 工作流程管理

像 **Temporal**、**Inngest** 和 **Windmill** 這樣的公司正在適應 Agent 工作流程，這些工作流程可能是長時間執行的、非確定性的，並且需要人工干預。

#### 狀態管理

Agent 需要複雜的狀態管理，跨越多個互動和上下文。像 **Replit** 的 Agent 狀態管理和 **LangGraph** 這樣的解決方案正在解決這些挑戰。

#### 監控和可觀察性

Agent 行為比傳統軟體更難預測和除錯。像 **LangSmith**、**Weights & Biases** 和 **Arize** 這樣的公司正在構建 Agent 特定的監控和除錯工具。

## 機遇與挑戰

這種基礎設施演進為創始人創造了巨大的機遇，但也帶來了獨特的挑戰：

### 機遇

1. **巨大的市場潛力**：隨著 Agent 采用的加速，對專門基礎設施的需求呈指數級增長
2. **差異化的技術要求**：Agent 工作負載與傳統應用根本不同，創造了新的技術護城河
3. **快速迭代周期**：該領域發展如此迅速，新進入者可以快速獲得牽引力

### 挑戰

1. **移動的目標**：Agent 模式仍在快速演進，使得構建持久的基礎設施變得困難
2. **複雜的整合**：Agent 需要與多個系統和服務無縫整合
3. **安全和合規性**：Agent 代表使用者行動引發了新的安全和合規挑戰

## 展望未來

AI Agent 基礎設施的演進才剛剛開始。隨著模式的固化和需求的明確，我們預期會看到：

1. **標準化的加速**：像 MCP 這樣的協議將變得更加普遍
2. **專業化的深化**：每個層次內的工具將變得更加專門化和強大
3. **整合的簡化**：更好的抽象將使 Agent 開發變得更加容易

對於創始人來說，現在是進入這個領域的最佳時機。基礎設施需求是明確的，市場正在快速增長，技術挑戰是真實的但可以解決的。

關鍵是要專注於解決 Agent 的特定需求，而不是試圖適應現有的傳統基礎設施。那些能夠構建真正 Agent 原生解決方案的公司將在這個新時代中蓬勃發展。
