# 深度解析 MCP 與 AI 工具化的未來

> 作者：`Yoko Li`  
> 原文：`https://a16z.com/a-deep-dive-into-mcp-and-the-future-of-ai-tooling/`

自 OpenAI 於 2023 年釋出函式呼叫功能以來，我一直在思考如何構建一個開放的智能體與工具使用生態系統。隨著基礎模型愈發智慧化，智能體與外部工具、資料和 API 的互動能力卻日益碎片化：開發者需要為智能體執行的每個系統和整合物件，實現具有特殊業務邏輯的智能體程式。

顯然，我們需要一個標準化的執行介面來實現資料獲取和工具呼叫。**API 曾是網際網路首個偉大的統一者——它創造了軟體間通訊的通用語言——但 AI 模型至今缺乏類似的標準化協議。**

2024 年 11 月推出的模型上下文協議（MCP）已在開發者與 AI 社群中引發強烈關注，被視為潛在的解決方案。本文我們將深入探討**MCP 的核心原理、它如何改變 AI 與工具的互動正規化、開發者基於該協議已構建的應用場景，以及仍需攻克的挑戰。**

讓我們深入探討。

## 什麼是 MCP？

**MCP 是一種開放協議，使系統能夠以跨整合通用化的方式為 AI 模型提供上下文。** 該協議定義了 AI 模型如何呼叫外部工具、獲取資料以及與服務互動。具體示例如下，展示了 Resend MCP 伺服器如何與多個 MCP 客戶端協同工作。

![MCP 插圖](https://d1lamhf6l6yk6d.cloudfront.net/uploads/2025/03/250319-Example-MCP-x2000-1024x455.png)

這個理念並不新鮮；MCP[從 LSP（語言伺服器協議）中汲取了靈感](https://spec.modelcontextprotocol.io/specification/2024-11-05/#:~:text=MCP%20takes%20some%20inspiration%20from,the%20ecosystem%20of%20AI%20applications) 。在 LSP 中，當使用者在編輯器中輸入時，客戶端會查詢語言伺服器以獲取自動補全建議或診斷資訊。

![MCP 插圖](https://d1lamhf6l6yk6d.cloudfront.net/uploads/2025/03/250314-LSP-x2000-1024x422.png)

MCP 的突破性在於其以代理為中心的執行模型：LSP 主要是反應式的（基於使用者輸入響應 IDE 的請求），而 MCP 旨在支持自主 AI 工作流。基於上下文，**AI 代理可以自主決定使用哪些工具、使用順序以及如何串聯工具鏈來完成任務。** MCP 還引入了人機協同能力，允許人類提供額外資料並批准執行流程。

![MCP 插圖](https://d1lamhf6l6yk6d.cloudfront.net/uploads/2025/03/250319-MCP-x2000-1024x541.png)

## 當前熱門的應用場景

藉助適當的 MCP 伺服器組合，使用者可將每個 MCP 客戶端轉變為"萬能應用"。透過[Slack MCP 伺服器](https://github.com/modelcontextprotocol/servers/tree/main/src/slack) 實現 Slack 通訊功能，利用[Resend MCP 伺服器](https://github.com/resend/mcp-send-email/tree/main) 完成郵件傳送，或透過[Replicate MCP 伺服器](https://github.com/deepfates/mcp-replicate) 進行影象生成。

以程式碼編輯器游標為例：雖然其本質是程式碼編輯工具，但作為優質 MCP 客戶端，終端使用者既可透過[Slack MCP 伺服器](https://github.com/modelcontextprotocol/servers/tree/main/src/slack) 將其改造為 Slack 客戶端，也能利用[Resend MCP 伺服器](https://github.com/resend/mcp-send-email/tree/main) 實現郵件傳送功能，或透過[Replicate MCP 伺服器](https://github.com/deepfates/mcp-replicate) 進行影象生成。更強大的應用方式是在單個客戶端整合多個伺服器以解鎖新流程：使用者可安裝[前端 UI 生成伺服器](https://github.com/21st-dev/magic-mcp) 從游標直接生成介面原型，同時呼叫影象生成 MCP 伺服器為網站建立主視覺圖。

除游標外，當前大多數用例可歸納為兩類：要麼是以開發者為中心、本地優先的工作流，要麼是使用大語言模型客戶端構建的全新體驗。

### 以開發者為中心的工作流

對於每日與程式碼為伴的開發者而言，一個普遍共識是"我不希望為了執行*x*而離開我的 IDE"。MCP 伺服器正是實現這一理想的絕佳方式。

開發者無需切換到 Supabase 檢視資料庫狀態，現在可以直接在 IDE 中使用[Postgres MCP 伺服器](https://github.com/modelcontextprotocol/servers/tree/main/src/postgres) 執行只讀 SQL 命令，透過[Upstash MCP 伺服器](https://github.com/upstash/mcp-server) 建立和管理快取索引。在進行程式碼迭代時，還可利用[Browsertools MCP 協議](https://github.com/AgentDeskAI/browser-tools-mcp) 為編碼代理提供實時環境以獲取反饋並進行除錯。

![MCP 插圖](https://d1lamhf6l6yk6d.cloudfront.net/uploads/2025/03/image1-1024x989.png)

*示例展示了游標代理如何透過 Browsertools 獲取控制台日誌和實時資料，從而更高效地進行除錯。*

在與開發工具互動的工作流之外，MCP 伺服器解鎖的新應用場景是透過[網頁爬取](https://github.com/mendableai/firecrawl-mcp-server) 或基於文件[自動生成 MCP 伺服器](https://mintlify.com/blog/generate-mcp-servers-for-your-docs) ，為程式設計 AI 代理注入高精度上下文。開發者無需手動配置整合，可以直接從現有文件或 API 啟動 MCP 伺服器，使 AI 代理能夠即時訪問工具。這意味著開發者可以減少樣板程式碼的時間消耗，將更多時間投入實際工具應用——無論是獲取實時上下文、執行命令，還是動態擴展 AI 助手的能力。

### 全新的體驗

儘管像游標（Cursor）這樣的 IDE 因 MCP 對技術使用者的強大吸引力而備受關注，但它們並非唯一的 MCP 客戶端。對於非技術使用者，Claude Desktop 作為優秀的入口級產品，使基於 MCP 的工具更易於大眾接觸和使用。很快我們將看到面向商業場景的專用 MCP 客戶端湧現，包括客戶支援、營銷文案、設計及影象編輯等領域——這些領域與 AI 在模式識別和創造性任務上的優勢高度契合。

MCP 客戶端的設計及其支援的特定互動在塑造其功能方面起著關鍵作用。例如，聊天應用程式不太可能包含向量渲染畫布，正如設計工具不太可能提供在遠端機器上執行程式碼的功能。最終，**MCP 客戶端體驗定義了整體 MCP 使用者體驗**——在 MCP 客戶端體驗領域，我們還有巨大的探索空間。

典型案例是 Highlight 如何透過在其客戶端實施[@命令](https://x.com/PimDeWitte/status/1899829221813334449) 來呼叫任何 MCP 伺服器。這催生了一種新的 UX 模式：MCP 客戶端可將生成內容管道傳輸至任意下游應用。

![MCP 插圖](https://d1lamhf6l6yk6d.cloudfront.net/uploads/2025/03/Notion-screenshot.png)

*Highlight 在 Notion MCP（插件）中的實施案例。*

另一個典型案例是[Blender MCP 伺服器](https://x.com/sidahuj/status/1901632110395265452) 應用場景：現在，几乎不了解 Blender 的業餘使用者可以透過自然語言描述想要構建的模型。隨著社群為 Unity 和 Unreal 引擎等其他工具部署伺服器，我們正在見證文字到 3D 的工作流程實時展開。

儘管我們主要關注伺服器與客戶端，但隨著協議的發展，MCP 生態系統正逐步成型。當前市場版圖覆蓋了最活躍的領域，但仍存在諸多空白。雖然我們深知 MCP 仍處於早期階段，*但隨著市場的發展和成熟，我們期待在地圖上新增更多參與者*（下一章節我們將探討其中部分未來可能性）。

![MCP 插圖](https://d1lamhf6l6yk6d.cloudfront.net/uploads/2025/03/250319-MCP-Market-Map-v2-x2000-1024x866.png)

在 MCP 客戶端領域，**目前所見的高品質客戶端大多以編碼為核心**。這並不令人意外，因為開發者通常是新技術的早期採用者，但隨著協議的成熟，我們預期將湧現更多以業務為核心的客戶端。

**當前大多數 MCP 伺服器採用本地優先策略且聚焦單機場景，這反映出目前 MCP 僅支援基於 SSE（伺服器傳送事件）和命令的連線方式**。然而我們預計，隨著生態體系將遠端 MCP 支援提升為一級功能，以及 MCP 采用[可流式 HTTP 傳輸協議](https://github.com/modelcontextprotocol/specification/pull/206) ，MCP 伺服器的採用率將顯著提升。

為支援 MCP 伺服器發現機制的實現，新一代 MCP 市場平台及伺服器託管解決方案正在湧現。[Mintlify](https://mintlify.com/) 旗下的[mcpt](https://www.mcpt.com/) 、[Smithery](https://smithery.ai/) 和[OpenTools](https://opentools.com/) 等平台正在簡化開發者發現、共享及貢獻新 MCP 伺服器的流程——這種變革類似於 npm 對 JavaScript 包管理的革新，亦如 RapidAPI 對 API 發現機制的擴展。該層級對於標準化訪問高品質 MCP 伺服器具有決定性意義，使得 AI 代理能夠按需動態選擇並整合工具。

隨著 MCP 協議集的普及，**基礎設施與工具鏈將在提升生態系統可擴展性、可靠性與可訪問性方面發揮關鍵作用**。Mintlify、[Stainless](https://www.stainless.com/) 和[Speakeasy](https://www.speakeasy.com/) 等伺服器生成工具正在減少建立相容 MCP 協議集服務的阻力，而 Cloudflare 和 Smithery 等託管方案正著力解決部署與擴展難題。與此同時，**[Toolbase](https://gettoolbase.ai/) 等連線管理平台**已開始最佳化本地優先的 MCP 金鑰管理與代理服務。

## 未來發展前景

然而，我們目前仍處於智能體原生架構演進的早期階段。儘管當前業界對 MCP 協議集充滿熱情，但在構建和部署 MCP 時仍面臨諸多未解決的挑戰。

協議下一版本需要解鎖的關鍵能力包括：

### 託管與多租戶支援

MCP 協議支援 AI 智能體與其工具間的一對多關係，但多租戶架構（如 SaaS 產品）需要支援多使用者同時訪問共享的 MCP 伺服器。預設採用遠端伺服器可能是短期內提升 MCP 伺服器可訪問性的解決方案，但許多企業仍希望自主託管 MCP 伺服器，並實現資料平面與控制平面的分離。

建立簡化的工具鏈以支援規模化 MCP 伺服器的部署與維護，將是推動更廣泛採用的下一個關鍵突破點。

### 身份驗證機制

當前 MCP 尚未定義標準的身份驗證機制來規範客戶端與伺服器的認證流程，也未提供 MCP 伺服器與第三方 API 互動時安全管理和委派認證的框架。目前身份驗證的實現方式取決於具體部署場景和開發實踐。在實際應用中，MCP 當前的採用主要集中在無需顯式身份驗證的本地整合場景。

更優的身份驗證正規化可能成為遠端 MCP 採用的關鍵突破口之一。從開發者的角度來看，統一方案應涵蓋：

- **客戶端身份驗證:** 使用 OAuth 或 API 令牌等標準方法處理客戶端-服務端互動
- **工具身份驗證:** 提供輔助函式或封裝器來實現第三方 API 的身份驗證
- **多使用者身份驗證:** 支援租戶感知的企業級部署身份驗證

### 授權機制

即使工具已完成身份驗證，仍需界定使用許可權的邊界與粒度。MCP 目前缺乏內建的許可權模型，訪問控制停留在會話層面——工具要麼完全開放訪問，要麼完全受限。雖然未來可能形成更精細的許可權控制機制，但當前方案依賴[基於 OAuth 2.1 的授權流程](https://github.com/modelcontextprotocol/specification/blob/5c35d6dda5bf04b5c8c76352c9f7ee18d22b7a08/docs/specification/draft/basic/authorization.md) ，透過身份驗證即授予整個會話的訪問許可權。隨著更多智能體和工具的接入，這種機制會帶來額外的複雜性——每個智能體通常需要攜帶獨立授權憑證的專屬會話，導致基於會話的訪問管理網路日趨複雜。

### 閘道器

隨著 MCP 協議集的規模化應用，閘道器可作為集中式層來處理身份驗證、授權、流量管理和工具選擇。類似於 API 閘道器，它將執行訪問控制、將請求路由至正確的 MCP 伺服器、處理負載均衡，並透過快取響應提升效率。這對於多租戶環境尤為重要，不同使用者和 AI 代理需要差異化許可權。標準化閘道器能簡化客戶端-伺服器互動，增強安全性，並提供更好的可觀測性，從而使 MCP 部署更具擴展性和可管理性。

### MCP 伺服器的可發現性與可用性

當前發現和配置 MCP 伺服器仍是手動流程，開發者需要定位終端節點或指令碼、配置身份驗證，並確保服務端與客戶端的相容性。新伺服器的整合耗時耗力，且 AI 代理無法動態發現或適配可用伺服器。

根據[Anthropic 在 AI 工程師大會](https://youtu.be/kQmXtrmQ5Zg?t=4927) 上月發表的演講，**MCP 伺服器註冊與發現協議即將問世**。這將為 MCP 伺服器的下一階段普及鋪平道路。

### 執行環境

大多數 AI 工作流需要連續進行多個工具呼叫，但 MCP 協議缺乏內建的工作流概念來管理這些步驟。要求每個客戶端都自行實現可恢復性和重試機制並非理想方案。儘管當前我們看到開發者正在探索[Inngest](https://www.inngest.com/) 等解決方案來實現這一目標，但將狀態化執行提升為一級概念將能為大多數開發者釐清執行模型。

### 標準化客戶端體驗

開發者社群經常提出的一個共同問題是：在構建 MCP 客戶端時應如何進行工具選擇？是否需要每個團隊都自行實現工具的 RAG（檢索增強生成）方案，還是存在待標準化的中間層？

除工具選擇外，目前也沒有統一的 UI/UX 正規化來呼叫工具（我們觀察到的實踐從斜槓命令到純自然語言呼叫應有盡有）。建立標準化的客戶端層用於工具發現、排序和執行，將有助於建立更具可預測性的開發者和使用者體驗。

### 除錯

MCP 伺服器開發者常常發現，要讓同一個 MCP 伺服器輕鬆適配不同客戶端十分困難。大多數情況下，每個 MCP 客戶端都有其獨特特性，而客戶端追蹤日誌要麼缺失要麼難以獲取，這使得除錯 MCP 伺服器成為極具挑戰性的任務。隨著業界開始構建更多遠端優先的 MCP 伺服器，我們需要新一代工具鏈來統一本地和遠端環境的開發體驗。

## AI 工具化的深遠影響

MCP 的開發體驗讓我想起 2010 年代的 API 開發。這個正規化嶄新而令人興奮，但工具鏈尚處於早期階段。如果我們快進到數年後，當 MCP 成為 AI 驅動工作流程的事實標準會怎樣？以下是若干預測：

- **開發者優先企業的競爭優勢將發生演變**，從交付最佳 API 設計擴展到同時交付最優的智能體工具集合。如果 MCP 協議集具備自主發現工具的能力，API 和 SDK 提供商需要確保其工具在搜尋中易於被發現，並在功能差異度上足夠突出以使智能體能為特定任務選擇它們。這種選擇標準相比人類開發者的需求可能更加細化和具體。
- **新型定價模式可能出現**：如果每個應用都成為 MCP 客戶端，每個 API 都成為 MCP 服務端，智能體可能根據速度、成本和相關性動態選擇工具。這可能導致更加市場驅動的工具採用過程，選擇效能最優且模組化程度最高的工具，而非當前最廣泛採用的那些。
- **文件將成為 MCP 基礎設施的關鍵組成部分**，因為企業需要設計具有清晰機器可讀格式（例如[llms.txt](https://mintlify.com/blog/simplifying-docs-with-llms-txt) ）的工具和 API，並基於現有文件將 MCP 伺服器打造成實際的標準產物。
- **僅憑 API 已不足以滿足需求，但仍是優秀的起點。** 開發者將發現從 API 到工具的映射很少是 1:1 的。工具是更高層次的抽象，對執行任務時的代理更具實際意義——代理可能不會簡單呼叫 `send_email()`，而會選擇包含多個 API 呼叫的 `draft_email_and_send()`函式以降低延遲。MCP 伺服器的設計將以場景和使用案例為中心，而非以 API 為中心。
- **新的託管模式將應運而生**，如果預設情況下所有軟體都成為 MCP 客戶端，其工作負載特徵將與傳統網站託管存在本質差異。每個客戶端本質上都是多步驟操作，需要可恢復性、重試機制和長時任務管理等執行保證。託管服務商還需在不同 MCP 伺服器間實現實時負載均衡，以最佳化成本、延遲和效能，使 AI 代理能在任意時刻選擇最高效的工具。

MCP 協議集已經在重塑 AI 代理生態系統，但下一階段的進步將取決於我們如何應對基礎性挑戰。如果實施得當，MCP 協議集可能成為 AI 與工具互動的預設介面，並開啟新一代自主、多模態、深度整合的人工智能體驗。

若 MCP 協議集能獲得廣泛採用，它可能從根本上改變工具的構建方式、消費模式和貨幣化路徑。我們期待見證市場對其的演進方向。今年將是關鍵轉折點：我們是否會見證統一 MCP 市場的崛起？AI 代理的身份驗證能否實現無縫對接？多步驟執行流程能否被正式納入協議標準？
